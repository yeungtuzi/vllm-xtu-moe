ROOT CAUSE of the ~5.5x sharded bloat = SYSTEM-WIDE THP='always':
  The engine's default NUMA shard path calls madvise(MADV_HUGEPAGE) on each node's region, but
  writes ONLY owned rows at full stride (~12.5% of each region). Under THP='always' the kernel
  promotes pages to 2MB THP REGARDLESS of madvise; a partial 4KB touch makes the WHOLE 2MB page
  resident -> the strided owned-row writes balloon resident to ~5.5x (657GB).
  Evidence: (a) XIAOTU_MOE_SHARD_HUGEPAGE=0 had ZERO effect while THP was 'always' (system
  overrides the madvise toggle); (b) once the user set THP='madvise', the SAME engine (no madvise)
  dropped to a ~157GB one-copy footprint at load, plateau 250.6-251.1GB (fast sharded, node-local).
  cpu_reclaim earlier also consistent: normal CPU frees return to OS; the 'always' THP was the hidden
  multiplier all along.

[SCALE-ANALYSIS] 逐层(layer-by-layer)流式 gpu_prefill —— 什么规模才合算
Date: 2026-09-07. 依据:实测 + 反编译(见 ref/lk_gpupre_decompile.md、vllm_gpupre_kernel_reference.md)。
目标语义更新:gpu_prefill = 手写 CUDA + 逐层流式(对齐 lk-moe 真实实现),NOT 标准 vLLM GPU MoE 全量驻留。

## 0. 硬性边界(为什么必须逐层流式)
- 模型 fp4 MoE(43 层)≈ 138GB(实测单层 w13 2.15GB + w2 1.07GB = 3.22GB);非MoE ~6.6-10.8GB。
- 单卡 40GB 全量驻留必 OOM(早前已实证:22261->39515MiB 后 OOM)。=> 只能逐层把单层权重搬进 GPU。

## 1. 逐层流式 GPU prefill 成本模型
每预算一次"完整 43 层 prefill forward"(任意 M 个 token):
  T_stream = 43 层 × 3.22GB / PCIe_bw      (搬的是权重,与 M 无关 = 固定地板)
           = 43 × 0.154s @20.9GB/s(实测) ≈ 6.6s
  T_compute(M) = M / GPU_prefill_tok_s      (GPU 计算;可测 ~10k+ tok/s => M/10000)
  T_gpu(M)  ≈ max(T_stream, T_compute(M))  (拷贝与计算可流水重叠)
  加上每层 launch/sync ≈ 43×~0.5-2ms ≈ 0.1s(次要)
  => 小 M 时由 ~6.6s 地板主导,大 M 时由 M/10k 主导。

## 2. CPU prefill 成本模型
  T_cpu(M) = M / CPU_prefill_tok_s(M)
  实测(xiaotu, server_cpuonly.log,prefix 0%):CPU prefill ≈ 330-363 tok/s。
  (lk-moe CPU AVX512 更强,但 gpu_prefill 特性存在正说明 CPU prefill 是短板)

## 3. 临界规模(合算点)
  令 T_gpu = T_cpu:
  6.6s = M/330  =>  M ≈ 2,180 token
  => 单个 prefill forward 的 token 数 > ~2,200 时,逐层流式 gpu_prefill 才相对 CPU prefill 合算;
     低于此,CPU prefill(~330 tok/s)比 6.6s 地板快。
  => 这也印证 lk 为何把触发阈值设在 1024(同一数量级;且触发阈值上浮到 ~2000 更贴理论断点,
     但 lk 用 1024 更保守地更早切 GPU 以吃大 batch 摊薄)。

## 4. TTFT 收益曲线(仅 prefill,decode 仍 CPU)
  token M | CPU TTFT(M/330) | GPU TTFT(max(6.6,M/10k)) | 加速
  --------|-----------------|--------------------------|------
  1k      | 3.0s            | 6.6s                     | 0.45x (更差)
  2.2k    | 6.6s            | 6.6s                     | 1.0x  (断点)
  5k      | 15.2s           | 6.6s                     | 2.3x
  10k     | 30.3s           | 6.6s                     | 4.6x
  50k     | 151s            | 6.6s                     | 23x
  100k    | 303s            | 10.0s                    | 30x

## 5. 生产实证锚点(lk-moe,80GB/2×A100-40GB,min_batch=1024)
  - gpu_prefill 瞬时 prompt throughput ~10,651 tok/s(02:02:12 日志),仅 GPU 可达。
  - 区间平均 2354 / 1661 tok/s(13:14:35 / 13:15:35,prefix 命中 91.9/94.2% 降低=新算 token 变多)。
  - 用户实测 GPU util ~100% 占约 1/3 时间(即 prefill 窗口),其余 40-50%(注意力+decode 重叠)。
  => 印证 gpu_prefill 只在"单个 scheduled batch ≥~1024 新 token"时触发;DSH 流量 prefix 命中 97.8%
     => 大部分 prefill 不足阈值走 CPU,收益集中在大新的 prefill。

## 6. 权衡与结论
  - gpu_prefill 收益 = TTFT 缩短,只对"长的新 prefill"明显;decode 永远 CPU(20-60 tok/s)。
  - 断点 ~2,200 token(实时 CPU prefill 吞吐决定);触发阈值应 >= 断点才合算。
  - 6.6s 地板假设权重每 pass 从 CPU 全量重流;若 lk 保留部分层窗口常驻 GPU,则地板降低、显存升高
    —— 这是 decompile(见 ref/lk_gpupre_decompile.md)要钉死的开项。
  - 对短 prefill(1k):gpu_prefill 反而更差(0.45x) => 阈值不能设太低。
  - 敏感度:PCIe 实测 16.2-20.9GB/s(单层 w13 2.15GB 物化实测 0.133s=16.2GB/s;20.9 为分离测得的
    原始带宽)。取 20.9 => 地板 ~6.6s/断点 ~2,200;取 16.2(0.154s/层) => 地板同量级(断点仍 ~2-3k)。
    断点与 CPU prefill 吞吐(330 tok/s)成正比,CPU 越慢,临界越低(越早切 GPU 越值)。

[DECOMPILE] lk_moe gpu_prefill 静态逆向结论(来源 run_gpupre/lk_gpu_prefill_analysis.md)
Date: 2026-09-07. 只读静态反汇编(cuobjdump/nvdisasm/readelf/strings),未启动 GPU/未碰 8070。

## 硬事实(A 级,符号/段直接确证)
- fatbin 非"只有 sm75":内含 sm_75/80/89/90 **四套原生 SASS cubin** + 2 host RTS stub。
  A100 运行时直载 sm80 cubin,**无 PTX JIT、无 NVRTC**。修正此前"只有 sm_75"的误读。
- gpu_prefill 内核 = `cutlass::Kernel<gemm::kernel::GemmGrouped<MmaMultistage<...>>>`。
  共 120 实例;tile = 128x256x32 / 256x128x32 / 128x128x32;
  activation = bf16 与 fp16(half)两套;weight = MXFP4(fp4 + fp8 e8m0 scale,block=32);
  bf16 标准 vs fp16 mixed 双变体;weight-stationary(B=per-expert fp4 常驻 SMEM,A=token 反复 supply)。
- **单次 gpu_prefill = 一圈 array-of-GEMM,一次 launch,无 43 层宿主逐层循环;M 不在 host 分块,
  而在内核内按 tile(128/256 行)分块,网格随 M 自动扩展。** grid 的 N 维按"每个 problem(=一层
  一专家 converging 块)占一个 colspan"切。
  => 这**修正/反驳**了"逐层计算 = lk 特有、宿主一层层循环"的假设:lk 是 **grouped 单发**,逐层
     体现在"每层作为一个 problem 组"、M 由内核内 tile 处理,而非宿主 for 循环逐层发射。

## 诚实声明:权重"全驻留 vs 逐层流式"静态无法最终裁决
- 支持"一次转换 + GPU 常驻":members 有 weights_gpu/expert_ids_gpu/input_gpu/output_gpu;
  宿主 API 全集(cudaMemcpyAsync/cuMemcpyHtoDAsync/cuMemAllocAsync/cuLaunchKernel_ptsz)均具备
  异步 stream 能力。
- 但 155GB 模型对 80GB 显存 => 全量驻留不可能 => 只能"子集驻留"。子集是"稀疏按 topk 选专家"
  还是"按层分组窗口"由静态无法分辨,需运行 profile(cudaMemcpyAsync 计数)才能钉死。
- 影响:如果 lk 无每-forward H2D 流式地板(权重重载),则我 scale-analysis 的 ~6.6s PCIe 地板
  只在"复刻 vLLM offloader 逐层流式"那套成立;若做"单发 grouped + 驻留子集",地板更弱/更高频。
  这是设计文档里标"待 decompile 钉死"的开项——现已确认**静态到此为止**,余项必须 profile。

## 与 vLLM offloader 的关系(设计取舍)
- 主线路 vLLM offloader/prefetch = 宿主侧逐层 H2D 预取 + slot 窗口(层循环在 host)。
- lk = 单发 CUTLASS grouped(层作为 problem 组,无宿主循环)。
- xiaotu 二选一:复刻 vLLM offloader 的逐层流式(有 6.6s 地板,规模合算点 ~2,200);或走 lk 式
  单发 grouped + 驻留子集(无地板但需解决"什么子集上 GPU"的运行时决定)。建议:以 vLLM offloader
  为工程化捷径(成熟、可配置),规模阈值见 [SCALE-ANALYSIS];lk 的真实子集选择留待 production profile
  (用户侧可做)。

1. **prod 的 2000+/1500 不是噪声,也不是 gpu_prefill MoE 加速**——是同款引擎在"大 batch"下
   CPU prefill + GPU(attention/logits/draft)**真实能力**的复现。
2. **修正规模分析**:此前用 CPU prefill ~330 tok/s 低估了。实际 lk 引擎大 batch CPU prefill 可达
   ~2000+ tok/s(本复制服 2268;prod 2354/1661;另 10651 为更极端短区间/口径)。
   => CPU prefill 吞吐随 M 显著上升(批摊薄),不是固定 330。
3. **gpu_prefill 在 lk 引擎上并未把 MoE 卸载到 GPU**:①nsys 证明 H2D 只有 19GB、0 大拷贝(权重没
   上 GPU);②33GB 显存装不下任何 MoE 层(138GB);③2628 tok/s 完全可由"CPU MoE + GPU 注意力"解释。
4. **对设计的影响**:逐层流式 gpu_prefill 的"6.6s 地板"若成立,断点应从 ~2,200 上移到
   ~10k+ token(因 CPU prefill 实为大 batch ~2000+ tok/s),更少场景值得;且本已实证"权重搬不上 GPU"。
   => gpu_prefill 对本机(40GB 级)的价值进一步被削弱;CPU prefill 在大 batch 下本身就很快。

## 未决
- 现有各次都无 MoE 权重 H2D;prod "10k"极端值与 2268 的 4-5x 差异,成因(极短区间/采样口径/个别
  gpu_prefill 命中)不在本次范围,标注为待用户 prod 侧核实(不影响主结论:2000+ 为 CPU+注意力)。

## [OFFLINE CPU prefill 实测 — 反驳 2000+](用户要求:离线无 vllm serve 无干扰 prefill 模拟)
用 lvllmds4-x env 的 lk_moe 直接构造 MOE_MXFP4(合成权重,只测吞吐;零权重对 FP4 反量化计时无影响),
对单层 cpu_prefill 计时 ×43 得完整 MoE prefill;配置 = prod 同款(256 专家,topk6,hidden4096,inter2048,groupN/K32)。
文件: process_data/run_lkreplica/offline_prefill_bench.py
结果(可复现,默认线程):
  M=1024 -> 43 层 = 545 tok/s
  M=2048 -> 43 层 = 573 tok/s
  M=4096 -> 43 层 = 542 tok/s
  M=8192 -> 43 层 = 477 tok/s
=> CPU MoE prefill ≈ 450-580 tok/s, 不是 2000+!

### 为什么日志说 2267.8 tok/s (且 prod 2354/1661/10651)?
vLLM v1 metrics.loggers:"Avg prompt throughput" = num_prompt_tokens.computed / delta_time,
delta_time = now - last_log_time(单次日志间隔)。本 fork 该行在请求完成时一次性打印,
delta_time 被压缩到 ~13s(而非真实 prefill 跨度),等于把整条 30k prefill 的 token 数除以短窗 → 虚高 ~5x。

### 两条独立证据都指向 ~500 而非 2000+:
1) 离线内核计时: 452-573 tok/s (M=8192 时 477)。
2) 复制服日志时间轴: 30k-token prefill 跨度 23:23:29->23:24:32 ≈ 63s => 30k/63 ≈ 480 tok/s (与离线 477@M8192 吻合)。
   (2267.8 实际 = 30k / 13.2s 的度量窗口假象。)

### 物理自洽(否决 2000+):
每 token 每层 topk6×(2×4096×4096 + 4096×2048) MAC ≈ 504 MFLOP → ×43 ≈ 21.7 GFLOP/token。
要 2000+ tok/s 需 ~43 TFLOP/s fp4——CPU 不可能。~500 tok/s ≈ ~10-11 TFLOP/s,fp4/AVX512-VNNI 算力天花板附近,合理。

### 纠错(DEVELOPER_DISCIPLINE #3):
此前(规模分析)把"CPU prefill=2000+"当实、把逐层流式断点定在~2200 附近——错误。
离线实测 CPU MoE prefill 实为 ~500 tok/s。故:
- 生产 2000+/1500 是**度量虚高**,不是真实 CPU prefill 吞吐。
- gpu_prefill 的价值账应收紧:CPU 基线 ~500 起(非 2000),手写 CUDA 逐层流式的收益判断需重估。

## [GPU_PREFILL 实证#3 — 决定性:GPU 真算 MoE,靠零拷贝省显存](09-08 复制服 nsys)
问:lk_moe 到底有没有真用 gpu_prefill?怎么只用那么点显存?
答:用了;GPU 真算 MoE;省显存靠"零拷贝读宿主机权重,从不落显存"。

### 证据(当前 gpu_prefill 配置 = prod 同款:MIN_BATCH=1024, PREFETCH_WINDOW=1)
1) 代码 dispatch(runner/moe_runner.py):M>=min_batch 且非 resident/mtp -> _gpu_prefill ->
   lk_moe.gpu_prefill(input,out,ids,weights,qlen,k,stream), GPU 张量 + CUDA stream。
2) 大 prefill 实测:TTFT=52.1s 处理 ~21600 token => 真实 prefill 415 tok/s(硬计量,非虚高)。
3) nsys 全量 131639 次 H2D 全部 <1MB(共34GB),无一 MoE 权重尺寸(每专家12.6MB/每层~GB):
   => MoE 权重从未被复制进显存。total 34GB << MoE 138GB。
4) LK_THREADS=32 纯 CPU MoE 内核离线实测 = 171-178 tok/s。而 415 ≈ 2.4x 远超。
   => 大 batch 的 MoE 不是 32 线程 CPU 能跑出的量级 -> 必然 GPU 加速。
5) GPU 全程 ~100%,显存 32.9GB(装不下 138GB 权重)= attention/KV/激活 + workspace。
6) lk_moe.MOE_MXFP4 确有 gpu_prefill 方法(闭源 .so);用未注册 CPU 权重单独调会 segfault
   => gpu_prefill 内核需要可被 GPU 访问的权重内存(HostRegister / host-mapped),即零拷贝。

### 唯一自洽机制:零拷贝 GPU MoE
gpu_prefill 的 CUDA 内核直接经 PCIe/NVLink 读宿主机(已 pin)的 fp4 权重,不在显存留权重副本。
=> 显存只要 attention+KV+激活(~33GB),权重 138GB 全程在 CPU RAM。这就是"只用很少显存"。

### 迭代纠错(DEVELOPER_DISCIPLINE #3)
- 前两轮把小 batch 无 H2D 泛化/把大 batch 当 CPU:错。
- 真相分两档:
  * 小 batch(M<1024):_cpu_prefill -> MoE 在 CPU(~146-180 tok/s,无权重 H2D)——旧结论此处成立。
  * 大 batch(M>=1024):gpu_prefill -> MoE 在 GPU 零拷贝(~415 tok/s,快于 CPU,显存不变)。
- 故 prod 极大 batch(2354 等)是"GPU 零拷贝 MoE + GPU attention"的真实能力,但 2000+ 数值仍
  受"Avg prompt throughput"窗口压缩虚高影响;TTFT 才是硬口径(本项目:52s/21k=415)。
- gpu_prefill 的"少显存"机制 = 零拷贝 host 权重,而非"逐层流式拷进显存"!(设计文档里设想的
  可能是"流式拷入+N窗口",但 lk 实际=零拷贝,连拷都不拷。)

## [分层拷贝 vs 零拷贝 — 实测](09-08 GPU2)
场景:显存放不下、必须混合推理(H2D→HBM 逐层算),不讨论"全放下"(人人都知全放下最优)。

### 机制对比
- 零拷贝(lk):GPU 内核内联读宿主 fp4 权重,sparse/跨页/延迟受限,有效带宽仅 2.65-8GB/s(PCIe 峰的~10-30%),实测 ~415 tok/s(全流水),显存≈0。
- 分层拷贝:专用批量 DMA 打满 PCIe(实测 26.5-26.8GB/s),与上一层计算可重叠,GEMM 从 HBM 读近峰值。

### 实测(staged_pipeline.py, 43 层流式, GPU2 空闲)
- PCIe bulk H2D: 26.5 GB/s(1/3.2/6.4GB 一致)= 每层 3.22GB → 122ms。
- 计算替身: 8192 token 1 层 GEMM = 3.5ms(≪122ms → H2D 主导)。
- 双缓冲重叠: 43层/M8192 = 5.16s → 1586 tok/s(PCIe 26.8GB/s 打满)。
- 串行(同缓冲):     5.27s → 1554 tok/s。
=> 分层拷贝流式 ≈ 1550-1590 tok/s ≈ lk 零拷贝 415 的 3.8x。这就是我们 vs lk-moe 的核心区别:
   我们占 1-2 层显存(3.22-6.4GB)但速度快 ~3.8x;lk 显存≈0 但慢。
- 注:overlap vs serial 当前几乎无差(计算 3.5ms 远小于 H2D 122ms),M/计算更大时才显现。替身非 lk 真内核(lk gpu_prefill standalone 复现不了/段错误),但上限推导对计算耗时稳健。

### 显存预留(用户实测 tip)
- vLLM 可用 --gpu-memory-utilization 0.8(用户实测可行)。40GB→32GB 给 vLLM,剩~8GB 放 staging。
- 1 层 3.22GB / 2 层 6.4GB 缓冲正好落在余量内 → 0.8 可行。
- 若要更大 staging 或不想 vLLM 碰,需在 vLLM 之外单独预留/预分配该显存。

## [公开带宽数据佐证 — 零拷贝 vs 页锁定异步拷贝](09-08 用户提供)
用户提供的公开测试实测带宽:
  零拷贝(Zero-Copy)           2.9-6.2 GB/s   (PCIe 3.0/4.0 典型)
  cudaMemcpyAsync(页锁定)      11.8 GB/s      (充分利用 PCIe)
  cudaMemcpy(可分页)           2.1 GB/s       (最差,隐式页锁定+拷贝)
  GPU 本地显存                249-500+ GB/s
结论:零拷贝带宽 ≈ 可分页 cudaMemcpy(慢),远低于页锁定异步拷贝,更远低于本地显存。
=> 与本机实测对上:lk 零拷贝有效 2.65-8 GB/s(落在公开 2.9-6.2 区间),我们的分层拷贝
   bulk H2D=26.5 GB/s(> 公开 11.8,A100-PCIE Gen4 x16)。故"分层拷贝(页锁定异步)>> 零拷贝"
   是机制层面的、独立于实机的实据。这正是选择"逐层 H2D→HBM 分层拷贝"而非零拷贝的硬背书。

## [XIAOTU gpu_prefill — 大 prefill 悬崖根因定位](09-08)
通过隔离 serve(serve_xiaotu_gpupref.sh,新增 SPEC/PREFIX/MOE_BACKEND/MBT 开关)锁定:

### 根因:MARLIN MXFP4 权重 repack 瞬时尖峰 + 单块大 prefill attention 内存 = 40GB OOM
1) gpu_prefill 确实触发并走到 `_ensure_gpu_prefill` -> `qm._setup_kernel` ->
   `prepare_moe_mxfp4_layer_for_marlin`(marlin_utils_fp4.py:640 `repack_weight`,对 256 专家
   torch.cat 转换 fp4 权重)。
2) 该 repack 有**大的瞬时显存尖峰**:翻译 7070-token 单块(no-spec)时,attention 已占 ~30GB,
   repack 再顶上 -> **CUDA OOM(38.95/39.49GiB)** -> 引擎崩。
3) 带 dspark spec 时是分块、峰值更低 -> 不 OOM 但慢/异常(前文 148s 悬崖的另一面)。

### TRITON 后端不可用(A100 死胡同)
- `--moe-backend triton` / `triton_unfused` -> `ValueError: backend 'TRITON' does not support
  current device cuda`。本 fork 里 MXFP4 的 TRITON 内核不支持 A100。
=> 本机 A100 可用的 vLLM 标准 MXFP4 后端基本只剩 MARLIN(带 repack 内存代价)。

### 实测对照总结(全 fresh,0% prefix)
| 配置 | 7070-token TTFT | 结论 |
|---|---|---|
| spec + prefix(首版) | 148.6s | 分块慢(悬崖) |
| no-spec + no-prefix(MARLIN) | 13.16s 但随后 OOM 崩溃 | 快但 repack 尖峰 OOM |
| fresh 3570(任意) | 4.08s / 2.9s | 稳定生效,875-1200 tok/s |
=> gpu_prefill 机制确定工作;40GB 上"大单块 + marlin repack"内存不足是拦路虎。

### 解决方向(落到实现)
- 计算内核在本 A100 只剩 MARLIN 可用 -> 必须绕开"prefill 进行中才 repack"。
- 正解(定稿方案的真正实现):**所有 43 层 gpu_prefill 内核在启动时一次性构建(共享同一块
  3.2GB 权重缓冲,逐层覆写)**,repack 在启动低内存时做一次,total;运行时只有 122ms/层小拷贝 +
  计算,无 repack 尖峰、无 138GB 驻留。需要自定义"多内核共享单缓冲"接线(现有 _ensure_gpu_prefill
  是 window=1 逐层 .to(cuda)+free,会在大 prefill 中 repack)。

### 结论
- 已证:分层拷贝单缓冲(window=1)机制对中等 fresh prefill(<=~3500)稳定生效、~875-1200 tok/s、
  显存有界。
- 拦路:大 prefill 的 marlin repack 内存尖峰(A100 又无 TRITON 替代)。
- 下一步实现:共享单缓冲 + 启动时一次建全部内核(把 repack 挪到低内存的启动段),或在 vLLM 之外
  自管理 staging 以避开与大 prefill attention 的竞争。

## [MARLIN 与"真·单缓冲"不兼容 + util 不是干净余量旋钮](09-08 隔离续)
新增实测(serve_util03.log / serve_mbt4096.log):
1) 降 util 救不了:gpu_memory_utilization 同时控 GPU KV 池与 CPU backend 预留(错误信息原话)。
   - util 0.5:KV 池吞满 20GB,idle 20.2GB 零余量 -> 大 prefill 时 repack 温 spike OOM。
   - util 0.3:连 KV cache init 都失败("No available memory for the cache blocks")。
   => 没有"给 repack 留余量"的干净旋钮。
2) MBT=4096(折半摘块)能让请求先活着(10.5s TTFT,完整响应),但第二块重材料化 43 层(window=1
   已把第一块的内核free)时,某层 repack 仍 OOM -> 引擎崩。摘块只是把悬崖推迟,没根治。
3) 根因实质:MARLIN 内核持有**每层专属的 repacked 权重(3.2GB/层)**;要"真·单缓冲(共享一块
   3.2GB raw 权重)"就必须有一个**读 raw(未repack)fp4 的核心里核**——MARLIN 给不了(它绑 repacked)。
   TRITON MXFP4 又不在 A100 上。
   => 定稿方案的"单缓冲"**需要自写/引用一个 lean fp4 内核读共享 raw 缓冲**(即最初"手写 CUDA"
      的本意),否则在 40GB 上大 prefill 必 OOM。
### 稳定现状(已多次复现)
- fresh <=~3500 token:gpu_prefill 稳定生效,TTFT 4.08s/2.9s(~875-1200 tok/s),显存有界不 OOM。
- fresh ~7070 token:MBT=8192 单块 -> 13s 后 repack OOM 崩;MBT=4096 两块 -> 10.5s 响应后仍 OOM 崩。
### 下一步(真正实现,需自写/引用 lean fp4 内核)
- 路线A:自写一个小而 lean 的 CUDA/Triton fp4 MoE 内核,从**共享单 raw 缓冲**逐层读算(43 层
  共享一块 3.2GB,无 repack、无 138GB 驻留)。这才是"真·单缓冲"。
- 或:换能容纳 138GB 的更大显存/多卡 -> 全驻留,违背本设计前提(装不下)。
- 若 lean 内核可行性待定,可退回"CPU prefill for all"(现状没 gpu_prefill 也可跑,~150-200 tok/s)。

## [FP8-on-CPU 先例 + 与 lk-moe 对比](09-08 调研,回答"非 nvfp4 特别需求,FP8 用 amx/avx512 有无案例")
- 结论:有可信先例。OSDI'26 论文(arxiv.org/html/2606.10493)在双路 AMD EPYC 9355 + 2×RTX 5090
  平台上用纯 AVX-512 做 FP8 MoE 推理,给可引用指标。
- CPU 无原生 FP8 单元(`vdpbf16ps` 只算 BF16),FP8 都借道 BF16:
  - 朴素法:FP8->FP32->scale/指偏->BF16->dot;>15 条指令,FP32 密度 16/512 位,吞吐 12 cycle/迭代。
  - post-scaling(Chitu 系):FP8 权重直扩 BF16 + `__m512bh` 激活 + `vdpbf16ps` 融合,512 位翻倍(32 元素)。
- 论文实测硬数字(同 EPYC9355 平台,DeepSeek-R1 671B):
  - FP8 GEMV 内核带宽:post-scaling+tiling = 815 -> 947 GB/s(OpenBLAS FP32 844;AOCL-BLAS FP32 992)。
  - FP8 全精度 decode:单流 ~21.5 tok/s;同模型 INT4 decode ~28 tok/s。
  - FP8 CPU prefill(AVX,2K 峰值)~500 tok/s,长程衰减;AVX FP8 vs KT AMX(INT4):20-32K 时 SLP 优胜 2.8×。
- 论文核心主张:别在 CPU 算 prefill,用 stream-loading 把 prefill 搬 GPU(SLP 1200 / DSLP 1800 tok/s)
  —— 与我们的 gpu_prefill 分层拷贝 H2D 方向完全同向,互为佐证。
- 与 lk-moe 对比(本机 AMD EPYC 9654 实测 vs 论文 EPYC 9355):
  | 引擎/模式 | prefill 吞吐 | 说明 |
  |---|---|---|
  | lk-moe 纯 CPU(本机实测) | ~150-200(48线程);~450-580(满核192@M8192) | 本项目生产真实值 |
  | lk-moe GPU 零拷贝 gpu_prefill | ~415 tok/s | 显存≈0 换 2.65-8GB/s,慢 |
  | OSDI FP8 AVX512(EPYC9355 双路) | ~500 prefill(2K峰)/21.5 decode | 别人平台 |
  | 我们规划的分层拷贝单缓冲 | ~1550-1590 tok/s | PCIe 26.5GB/s 打满,lk 零拷贝 3.8× |
- 机制级结论:AMX 提升算力(TFLOPS),但 MoE decode/prefill 带宽受限;长 prefill 无论 AMX/AVX 都
  被砍到 30s TTFT 外 —— 瓶颈是 CPU 内存带宽,不是 ISA。lk-moe 未被通用 FP8-on-CPU 超越(同一量级)。
- 战略含义:计算层(FP8/amx/avx512 内核)非独家竞争力(论文+vLLM 主线都有,都能到带宽上限附近);
  真正独有的是"逐层 H2D 单缓冲分层拷贝把 PCIe 打满(1550-1590 vs lk 415)"——分工层的显存/带宽
  编排才是护城河。详见 ref/xiaotu_cpu_expert_mainline.md。

## [fork vs 主线插件 决策分析 + 100tok/s 带宽账](09-08)
- 决定性事实:用户实测 48/96/190 核性能都差不多 → decode 带宽受限(非内核算术),带宽=硬件属性,
  与谁写内核无关 → 同一内核同一硬件上限必一样。**计算内核这条腿,两条路性能无差异**。
- 100 tok/s 带宽账:单 token decode 读激活权重 ≈3.246GB(topk6/43层);100 tok/s≈325 GB/s
  (EPYC9654 现实 ~600-690 的 ~50%),可行。瓶颈不在内核,在内存带宽,不认宿主。
- 两条路真正不同:编排责任/维护成本/生态站位;性能持平。主线量化 CPU 内核全要求 AMX(Intel);
  本机 AMD 无 AMX → 只有我们的内核能在这台机跑 MXFP4/FP8,非可有可无。
- **唯一致命未知数**:主线插件能否拿到 fork 相同的 NUMA 分片/线程绑定控制权(325GB/s 能否堆满)。
  这决定第二路能否保住 100 tok/s。详见 ref/fork_vs_mainline_plugin_decision.md。

## [步骤③实证:NVMA/绑核控制权主线已暴露,第二路开关通过](09-08,main 分支源码实测)

## [M2-2 实证:主线原生 PrefetchOffloader 也救不了 DS-V4 on 40GB(09-08,GPU2/8071 实测)]
- 用主线原生 offload(--offload-backend prefetch, --offload-group-size 8 --offload-num-in-group 2
  --offload-prefetch-step 2, --offload-params "w13_weight,w13_weight_scale,w2_weight,w2_weight_scale")
  在 GPU2/8071 起 serve。
- 结果:"Offloader set to PrefetchOffloader" 成功激活,但仍 OOM:
  model__init__ -> DeepseekV4Model(1781) 构造时,某个 **2GB 连续分配**(try allocate 2147483648,
  free 737MB)失败。即模型构造会在 offloader 介入前就把 GPU 吃到 ~41GB(in total 42GB)。
- 根因(诚实):主线 offloader 是"forward 前/前向中把已构造的权重从 CPU 搬 GPU"的机制(偏
  KV/已加载权重的驻留),但 DS-V4 **模型构造阶段 initialize_model 就在 GPU 上赋初值/建大参数**,
  offload 无法阻止构造期 OOM。=> 原生 offloader 对"模型本身太大、构造即满"的 DS-V4 不设解;
  它被设计成原子(权重加载后再 offload),不是"减少并发构造峰值"。
- 结论修正:主线原生 offload **不是**比自写 xiaotu hybrid 更简单的捷径 —— 至少在 DS-V4 on
  单 40GB 上,构造期就 OOM。要让模型能构造成功,必须真把每层 ffn 换成 CPU(自写 hybrid,即
  _wrap_cpu_ffn),或大幅降低初始 GPU 分配(如 lazy 加载,本已开)。
- 但 offload 机制仍可用于**已构造成功**后把部分权重搬 CPU/省显存(与我们的 gpu_prefill 单缓冲
  编排方向一致,可借)。待模型能构造后再评估。
- 安全:GPU2 已释放,prod 未动,无残留进程。两次 OOM 均干净退出,无副作用。

## M1-M2 桥:真实 E=256 CPU 吞吐(决定性,2026-09-08)
[决定性]脚本 scripts/m1_bench_e256.py + scripts/e256_time.py(scp 至 vllm-xiaotu-moe),
读真实 layer-3 全部 256 routed experts(shard model-00005)建 xiaotu MOE_MXFP4(gk32 raw e8m0),
EPYC 9654 实测(显式 OMP=96/32,GPU2 无关,纯 CPU cpu_prefill):

  B(批) | 单层ms | 43层ms | 天花板 tok/s(MoE-only)
     1  | 2.2-10.6| 93-457| 2-10
    32  | 8.0    | 344   | 93
    64  | 13.0   | 560   | 114
   128  | 21.1   | 907   | 141
   256  | 35.6   | 1531  | 167

【关键洞见】fork 的 ~100 tok/s 是"带批的吞吐"数字,不是单流延迟!
  - 单 token decode 延迟受限(~2-10 tok/s),与用户"48/96/190 核都差不多"完全吻合(单流不随核涨)。
  - 一旦带上批(B>=64),引擎把每层"本批激活的专家权重读一次、整批共享",吞吐反而高出单流 1-2 个量级:
    B=64~167 tok/s 都 >100。=> 我们的主线插件要走通 ~100 tok/s,关键在让 vLLM decode 保持 batch>=~64
    (max_num_seqs 合理 + 不因单 token 卡死),不是写不写主线模块本身。
  - 带宽账对上了:全模型 138GB fp4;B=256 时每层读全部 256 专家(3.2GB/层)×43 ≈138GB/批;
    35.6ms*43=1.53s/批 → 有效 90GB/s(引擎只吃单 NUMA node 12ch)。未到 600-690 理论(单 node ~300),
    说明引擎未完全带宽饱和(OMP 线程数有影响:B=1 时 OMP=96 比 OMP=32 快 ~5x)。
【可靠性发现】引擎 NumaWorkPool 在"紧循环连续多次 cpu_prefill"(同一引擎背靠背 5 次)下偶发
  SIGSEGV(worker_loop 读 freed/poison 0xd3/0x4f 内存,use-after-free 竞态),OMP=96 过订阅更易触发;

## 纪律#1 广搜结果:vLLM 官方 MoE 专家 CPU 卸载(PR #37190)——评估(2026-09-08)
[搜到的现成轮子]
- vLLM **PR #37190**:`--moe-expert-cache-size N` + `--moe-expert-cache-split {token,expert}`,
  新增 `vllm/model_executor/layers/fused_moe/expert_weight_provider.py`(CachedWeightProvider),
  docs/features/moe_cache_policies.md;改 routed_experts.py / moe_runner.py / fused_moe_method_base.py
  / fp8.py / unquantized_fused_moe_method.py。**未合入我们这版 6c73b08**(全库 grep 无 moe_expert_cache)。
- 相关:RFC #33869(DeepSeek-R1 MoE offload)、PR #49321(W4A16 cold-expert CPU offload,HIP/in-graph);
  ktransformers(kvcache-ai,CPU 内核混合推理)、SGLang PR #12586(expert deferral)。
[机制实证(读 diff 源码,不是二手转述)]
- `CachedWeightProvider`:全部专家权重在 **CPU pinned 内存**,GPU 只留 capacity 个 slot 的 scratch buffer;
  LFRU(freq/age)淘汰;**未命中 -> H2D 拷进 slot** -> `kernel.apply(w1,w2,expert_map)` **在 GPU 上算**。
- 即"**CPU 存 + GPU 算**",**不是**"CPU 上 AVX/AMX 计算"(外部 AI 那句对不上这个 PR)。
- 量化支持:该 PR 首版给 fp8 + unquantized(`supports_expert_lru_cache()`);**不含 mxfp4/fp4**。
- 限制:不兼容 EP>1 / DP / SP;缓存必须 >= top_k。
- 扩展点:注释明确"kernel 不知道也不关心权重从哪来"——**WeightProvider 是可插拔接缝**。
[对我们的含义/建议]
- 对 GLM-5.3-Flash(fp8,A100 fp8 内核 SM80-OK):PR #37190 是**可复用的现成方案**(若打上该 PR),
  但它是 unmerged、且 GPU 算(每次未命中走 PCIe H2D 搬专家权重)。
- 对 DS-V4-Flash(fp4):PR 首版不支持 fp4,且 GPU fp4 内核在 SM80 有问题。
- 我们的 xiaotu 引擎走 **CPU 算**(权重不搬 PCIe,只搬 tiny 激活),已实测 110-167 tok/s;
  与 PR 的"CPU 存+GPU 算"是**互补**,不是替代。
- **推荐**:复用 PR #37190 的 **WeightProvider 抽象**,把 xiaotu 引擎实现为一种
  "CPU-compute provider"(权重留 CPU 且计算在 CPU),而不是另起炉灶重造卸载编排。
  这样既守纪律#1(用上游接缝),又保留我们的核心资产(无 AMX 的 AVX512-VNNI CPU 内核)。

## 混合模式数值差的根因确认(gpt-oss 是特例,不是引擎错)(2026-09-08 夜)
[实据]models/gpt_oss.py:389 `FusedMoEFactory(..., has_bias=True, activation="swigluoai")`。

  => 对 DS-V4/GLM,混合模式的 MoE 数值没有引擎侧障碍;唯一障碍是它们的 **sparse-MLA 注意力在
     A100 上无后端**(SM90/100 only)→ 正是 SM80 移植要解决的。
[结论]gpt-oss 用于验证"机制通"(已达成);"数值正确"应换 silu+无 bias 的模型或用 DS-V4/GLM
  (待 SM80 注意力打通)。可选:给 apply 补 swigluoai+bias 以支持 gpt-oss(引擎闭源 → 需在
  apply 侧用 torch 补,或在引擎加 variant)。

## o_proj 卡点根因确认:int32 打包的 fp8 权重(2026-09-08 深夜)
[实测]wo_a.weight=(256, 32768) **dtype=torch.int32**,in=4096,out=8192,
  weight_scale=(32, 8192),z=(8192,8,1024),o_fp8=(8192,8,4096)。
[解读]逻辑权重 [8192, 4096] fp8(33.5MB);主线把它**打包成 int32**(4 个 fp8/int32):
  8192*4096/4 = 8.39M int32 = [8192,1024] int32 = view 成 [256,32768]。DeepGEMM fp8_einsum 吃这个打包布局。
  fork 的 deepseek_v4_fp8_einsum 期望**未打包** b=[groups*out_rank, hidden]=[8192, 4096] uint8 → 形状不符。
  => 两侧的 fp8 权重存储方式不同(主线 DeepGEMM 打包 int32 vs fork MarlinFP8 不打包)。
[torch fallback 方案(下一步实现)]在主线 o_proj.py 里,当 is_deep_gemm_supported()=False 时:
  1. w_u8 = wo_a.weight.view(torch.uint8).reshape(8192, 4096)  # 解包(内存序保持 row-major)
  2. 按 weight_scale 反量化成 bf16
  3. z = torch.einsum("bhr,hdr->bhd", dequant(o_fp8,o_scale), w_bf16.reshape(8,1024,4096))
  需确认 weight_scale 的 [32,8192] 语义(应为 [k/128, n] 块缩放)与 o_scale 的布局。
[状态]主线 o_proj.py 仍带调试打印(待清理);此 fallback 未实现。

## [TP=2 启动失败的真正根因(两次都栽在这)](2026-09-09 13:2x)
- 现象:`Engine core initialization failed ... WorkerProc wait_for_ready`(EOFError 分支),
  worker 在**建引擎途中**静默消失,EngineCore 随后 SIGTERM/SIGKILL 另一个 worker。
- 根因(`journalctl -k`,**内核 OOM killer**,不是 vLLM 超时):
  - lp_tp2c:12:59:16 `Out of memory: Killed process 497910 (VLLM::Worker_TP)
    total-vm:1058081392kB, anon-rss:505005236kB`(单 worker 505 GB RSS!)
  - curve_tp2:13:19:17 同样,Killed process 504486,anon-rss 430 GB。
  - OOM 报告里 `Node 0 Normal free:108452kB ... inactive_anon:193319756kB
    all_unreclaimable? yes` → **node 0 被打满**(其余节点还有 144 GB 空闲)。
- 为什么这么大:未设 `XIAOTU_MOE_SINGLECOPY=1` 时,引擎会把权重按 socket 复制
  (`moe_v2.hpp` 的 `numa_socket_alloc(bytes, s) for s in 0..1`),每个 worker 持
  ~2.7 份 156 GB 权重 ≈ 420-500 GB。TP=1 时单个 worker 还能塞进 1.5 TB,TP=2 两个
  worker 就必然打爆 node 0。
- 修法:`XIAOTU_MOE_SINGLECOPY=1`(serve_8071.sh 本来就有,我的 TP=2 命令行漏了)
  + `VLLM_ENGINE_READY_TIMEOUT_S=3600`(默认 600 s 也小于加载耗时,是**另一个**独立问题)。
- 教训:看到 `wait_for_ready` EOF 不要只怀疑超时,先 `journalctl -k | grep -i oom`。

## [第 2 轮:带宽/编译器/并发/BF16 四项调查 + 项目改名](2026-09-09 16:5x)
### 1. 内存带宽 422 GB/s 之谜解开(用户提问)
规格:**DDR5-4800 × 24 条 = 921.6 GB/s 理论**。实测 2×2×2 归因:
| 线程 | 放置 | 普通写 | NT 写 | 只读 |
|---|---|---|---|---|
| 96 | first-touch 本地 | 574.8 | **743.6** | 754.5 |
| 96 | interleave=all | 386.9 | 397.7 | 440.8 |
| 192 | first-touch 本地 | 507.8 | 647.0 | 714.0 |
| 192 | interleave=all | 398.6 | 461.7 | 456.3 |
- 单流只读 96 线程 **860.5 GB/s = 93% 理论** → 硬件健康。
- 归因:页放置 interleave→first-touch **+87%**;普通写→NT **+29%**;192→96 线程 **+15%**;
  向量宽度/-ffast-math/-mtune **无影响(<1%)**。
- 工具:`report/stream_nt.c`(AVX-512 NT 存储)、`report/rd1.c`(单流只读)。

### 2. 编译器参数有没有 Zen4 空间?→ 没有
- GCC 11.4 **不认识 znver4**(`-march=znver4` 报错),`-march=native`=znver3 + 默认 128 位向量。
- 5 组参数 A/B(512/256 位、mtune=generic/znver3、unroll、fast-math)在 **STREAM** 和
  **xiaotu CPU 引擎**上互差 <1%。原因:STREAM 96 线程已内存受限;引擎热循环是手写
  AVX-512 BF16 内联函数,编译器向量化器不参与。
- 引擎实测 **0.64 TFLOP/s = AVX-512 BF16 峰值(~11 TFLOP/s)的 6%**,每层只读到 3.2 GB/s
  → **不是带宽受限、也不是编译器受限,是反量化 ALU / kernel 结构受限**。

### 3. 用户提问:预反量化成 BF16 能否大幅提速?→ 不能(~1.2×)
`scripts/bench_cpu_engine_bf16.py`:同一层真实权重、同一路由,MOE_MXFP4 vs MOE_BF16。
- B=2048:MXFP4 962–1160 ms(0.53–0.64 TFLOP/s)vs BF16 956 ms(0.65 TFLOP/s)→ **1.2×**。
- B=512:BF16 反而慢 2×(M=1 matvec 路径)。
- **反量化最多占 ~17%**。更关键:**每 token 成本随 batch 恶化**(B=512 0.28 ms/tok →
  B=2048 0.57 ms/tok),两种格式都只有峰值 5–9% → 瓶颈在引擎 kernel 结构,不在权重格式。

## [通用化盘点:ISA 与格式的现状/缺口](2026-09-09 18:0x)

- **ISA 基础设施已在位**:`loader.py` 有 5 级运行时阶梯(scalar/avx2/avx512_base/
  avx512_vnni/avx512_bf16),`xiaotu-moe/scripts/build_variants.sh` 一次能编 5 个变体;

## [⚠️ 更正:CPU 引擎瓶颈结论 + 微基准路由 bug(用户指出)](2026-09-09 18:3x)
用户指出:"你又说瓶颈是反量化 ALU,但我们用预先反量化的 BF16 权重测过收益不怎么样"。
核查后确认**我错了,而且错了两处**:
1. **微基准的路由是错的**:`scripts/bench_cpu_engine.py` 原本 `np.tile(ids,(B,1))`,
   所有 token 命中**同样 6 个专家**(每专家 2048 行);真实模型是 256 专家 × ~48 行。
   固定路由把权重工作集从 3.2 GB(DRAM)压到几十 MB(L3)。
2. **BF16 对照不是同一个 kernel**:MXFP4 是批处理(M=每专家行数、4 行分块),
   BF16 走 `matmul_bf16(..., M=1, ...)` 的矩阵-向量乘 —— 结构不同,不能隔离反量化。

修正后的实测(96 线程,逐 token 随机路由,引擎自带 XIAOTU_MOE_PROFILE=1 相位计时):
| B | 每层 | 每 token/层 | 算力 | A(gate_up) | B(down) | C(组合) |
|---|---|---|---|---|---|---|
| 512 | 89.1 ms | 0.174 ms | 1.73 TFLOP/s | – | – | – |
| 2048 | 315.7 ms | 0.154 ms | 1.96 TFLOP/s | 182 ms | 88 ms | 8.6 ms |
| 8192 | 1235.0 ms | 0.151 ms | 2.00 TFLOP/s | – | – | – |
- **1.7–2.0 TFLOP/s = AVX-512 BF16 峰值(11.4)的 15–18%**(不是 0.64/6%);
- **99.7% 时间在两个 GEMM 相位**;**权重流量 ~10 GB/s**(机器可做 740)⇒ 不是带宽受限;
- **每 token 成本随 batch 改善**(0.174→0.151),不是恶化;
- **反量化占比仍未确定**(需要给同一个批处理 kernel 加"跳过解码"开关才能测)。
- **BF16 预反量化在真实路由下慢 14×**(320 ms → 4628 ms),不是快 1.2×。
- 顺带发现:真实模型 CPU prefill 2.15 s/层 vs 隔离引擎 0.32 s/层 ⇒ **6.7× 差距来自
  混合路径的每层开销**(D2H/H2D、逐层引擎调用、43 个引擎各自的 scratch),是 CPU 侧
  下一个真正的优化点。
已更正:EXPERIMENT_REPORT §1.4/§7.2b(新增)/修订记录第 12 版、ROADMAP_GENERALITY §1.2
(第 2 版)、OPTIMIZATION_ROUND2 §4b(第 2 版);并修好两个 bench 脚本的路由。
