# 大规模集群设计:异构解耦 + 集群级 KV 池(规划)

> **状态:规划(设计方案,未实现、未实验)**。
> 本文把两份既有讨论**合并扩展**:
> ① 早期的"**MoE 专家池横向扩展**"设计(注意力/预填充留 GPU,CPU 节点承担 MoE 专家,含全部实测数据);
> ② 近期的"**多副本统一入口 + 共享缓存**"规划(LiteLLM 网关 + LMCache 分层 + 共享 L1/L2)。
> 并扩展到目标规模:**1600 台纯 CPU 节点 + 160 台 8 卡 GPU 节点 + 100 GB/s IB + 无单点 + 自动伸缩**。

## 2. 来自早期设计的实测依据(全部是本仓库实测,不是估算)

| 量 | 实测值 | 对集群设计的含义 |
|---|---|---|
| 每 token 激活的专家权重(43 层) | **3.246 GB** | 决定 MoE 侧的带宽需求 |
| 引擎边际流式带宽(24 通道 DDR5) | **692–768 GB/s**;机器上限 ~740 GB/s | 单机专家池的上限 |
| 引擎每层固定成本 | **A ≈ 0.124 ms/层**(与字节、行数无关) | ⚠️ **不随节点数下降** ⇒ 43 层串行是**硬边界** |
| 单机 EP 归约(`/dev/shm`) | **~14 µs/层** | 跨机必须换成网络,这是唯一要新写的部分 |
| **纯 GPU 地板**(注意力等,C=1) | **16.8 ms/token** | ⇒ **注意力必须留在 GPU**(延迟敏感 + 需 kernel) |
| 31 层 CPU MoE(C=1) | **7.4 ms/token**(0.24 ms/层) | CPU 侧确实能算 MoE |
| 一个 token 的 KV(fp8_ds_mla,8k ctx) | **~0.196 MiB/token** | ⇒ **768K 前缀 ≈ 150 GB / 每序列**;8K ≈ 1.6 GB |
| 非专家权重(注意力 + dense) | **5.96 GiB** | 前段显存预算 |
| ⚠️ 线程池 park 耦合 | `spin_idle` 调优实测 **35.6 s → 5.97 s(−83%)** | ⇒ **集群化前必须先标定 worker 常驻策略**,否则测出的"集群折损"会混入可消除的调度开销 |

**早期设计的结论(原样继承)**:单流 **26.1 ms/token**;4 台为一组的方案 B 预估 **~20.5 ms(~49 tok/s)**,
C=4 聚合 **180–220 tok/s**;**MoE 侧完全不需要 GPU**;**每层固定成本 A 不可分摊**。

## 3. 形态选择:CPU 机群扮演什么角色(**必须先定**)

### 3.1 两种已被我们数据支持的角色

| 角色 | 机制 | 依据 | 收益 |
|---|---|---|---|
| **A. MoE 专家池** | CPU 节点承担 43 层 MoE 专家计算,GPU 侧只做注意力/KV/预填充 | 31 层 CPU MoE = 7.4 ms/token;MoE 是**带宽密集**;CPU 机器 700 GB/s | 摊薄带宽、GPU 不再被稀疏专家占满 |
| **B. KV-cache pool 节点** | CPU 节点的 **DRAM 作为集群 KV 池**(RDMA 可直读) | 单机 1.5 TB DRAM;**1600 台 ≈ 2.4 PB** 池容量 | 前缀 KV 集群级复用 ⇒ **免 prefill** |

### 3.2 ✅ 澄清:CPU 机群跑的是"**MoE 的解码部分**"(每 token 的专家计算),不是整个 decode

用户 2026-09-24 澄清:CPU 节点负责 **MoE 解码**(每个 token 的专家前向),**注意力仍在 GPU** ✓
⇒ 这与早期设计**完全一致** ✓(早期设计正是"MoE 计算从 decode 实例里分出去"),**不存在冲突** ✓

```
每个 decode step:
  GPU(P 侧):注意力 + KV + 采样 + (可选)常驻专家层      ← 延迟敏感、需 kernel
  CPU(专家池):该 token 的 MoE 专家计算(43 层里的 31 层)  ← 带宽密集
```

### 3.2.1 ⭐ 关键选择:规模到 1600 台时,应当"**每台一份完整专家集**"

| 形态 | 机制 | 优点 | 代价 |
|---|---|---|---|
| **O1 复制式(推荐,大规模)** | **每台 CPU 节点都存完整专家集**,各自服务自己的 token | **无跨机归约** ✓(早期设计的最大风险消失);**吞吐线性扩展** ✓;任意节点可服务任意 token ⇒ LB 自由 | 每节点需 **137 GiB** DRAM 放权重(1.5 TB 节点完全够 ✓) |
| **O2 切分式(早期设计)** | 一组多台**切分同一 token 的层**,跨机归约 | 单 token 的每层字节降到 1/N | 43 次/token 跨机同步 ✗;**固定成本 A 不可分摊** ⇒ 单流仅 26.1→20.5 ms(几乎持平) ✗ |

**实测锚点(本仓)**:
* 31 层 CPU MoE = **7.4 ms/token**(单机全量)⇒ 单机 MoE 吞吐 ≈ **135 tok/s**
* 折算有效带宽:2.34 GB(31×75.5 MB)/ 7.4 ms ≈ **316 GB/s**,而机器上限 ~740 GB/s ⇒ **引擎效率 ~45%**(有优化空间)
* ⇒ **1600 台 O1 形态的 MoE 聚合吞吐 ≈ 1600 × 135 ≈ 21.6 万 tok/s**(按实测速率;若效率提到 100% 则 ~50 万)

### 3.2.2 "每个 P 带多少 D"的分析框架(待实测确定)

* 单 **P 实例**(GPU,TP=2)的**注意力地板 = 16.8 ms/token** ⇒ C=1 约 **60 tok/s**;
  并发下批处理会显著提高(实测同型配置 C=4 端到端 **107 t/s**,为 C=1 的 ~3×)
* ⇒ **比例应由"GPU 注意力"这一侧决定**,而不是由 CPU 侧决定:
  160 GPU(8 卡 ⇒ TP=2 ⇒ **640 个 P 实例**)对 1600 CPU 节点 ⇒ **每 P 实例约 2.5 个 CPU 节点**(即每台 8 卡机约 10 个 CPU 节点)✓
* ⚠️ 这个 **10:1 是合理起点但未实测**:需按"目标并发下的 GPU 注意力吞吐"与"CPU MoE 吞吐"配平,并按 §11 清单实测调整

### 3.2.3 CPU 节点的第二种用途:**KV 池的宿主**(两种角色可共存)

每台 CPU 节点:权重占 **137 GiB**,剩余 **≈1.35 TB** 可作 **KV 池** ⇒
**1600 台合计 ≈ 2.16 PB** 的集群 KV 池 ✓ —— 与 §7 的 L1.5 层完全对应 ✓

## 4. 网络:两股流量性质完全不同(**合并两份讨论的关键**)

| 流量 | 量级 | 性质 | 要求 |
|---|---|---|---|
| **MoE 层间归约**(跨机) | 每层 16–64 KB;43 层 ≈ **0.7–2.7 MB/token** | **小消息、极低延迟** | 100 tok/s ⇒ 仅 **70–270 MB/s** ⇒ **25–100 GbE + RoCE 足够** |
| **KV pool 读写**(前缀 KV) | 单序列 8K ≈ **1.6 GB**;768K ≈ **150 GB** | **大块、带宽密集** | ⭐ **必须有高带宽**(见下) |

**KV pool 的带宽算术(100 GB/s IB ≈ 800 Gb/s)**:

| 场景 | 传输量 | 100 GB/s 下耗时 | 对比重算 |
|---|---|---|---|
| 2K 前缀 | ~0.4 GB | **~4 ms** | 数十秒 |
| 8K 前缀 | ~1.6 GB | **~16 ms** | 26.7 s(实测,10K 前缀) |
| 768K 前缀 | ~150 GB | **~1.5 s** | 数十分钟 |

⇒ ⚠️ **关键设计约束**:**decode 节点必须把"当前序列的 KV"保存在本地 DRAM** ✗
若让 decode 每步都从池里读全量 KV,则 8K 序列 @50 tok/s ⇒ **80 GB/s** 的持续流量 ⇒ **网络瞬间打满** ✗
⇒ 正确形态:**池只服务"前缀复用/移交",不服务"每步读取"** ✓(池 = 冷热层;活跃序列的 KV 在本地)

## 5. GPU 机群(160 台 × 8 卡 = 1280 卡):角色划分与实例粒度

* **角色**:**prefill + 注意力 + KV 持有 + (可选)常驻专家层 + draft/投机** —— 即"延迟敏感且需要 kernel"的部分
* **实例粒度**:沿用已验证形态 **TP=2**(每实例 2 卡)⇒ 单机 8 卡可跑 **4 个实例**;
  若要更长上下文/更大 KV,可改成 TP=4(每机 2 实例);**以显存与 KV 目标长度为准,属于待定项**
* **卡型**:**沿用已验证的 A100/SM80 是零风险选择**(我们全部补丁与 kernel 都在 SM80 验证);
  换 SM120 等新卡需**单独适配**(稀疏 MLA 走另一条 vLLM 代码路径)⇒ 见 §10 风险
* **多模态**:**MM 处理(视觉塔/图像 patch)发生在 P 侧**,decode 侧只生成
  ⇒ 因此"3 个模型均多模态"对 D 侧/池侧**无额外要求**,只影响 P 侧显存与 prefill 激活
* **每模型实例数**:先按经验配比,后续按 §8 自动伸缩;`P:D` 比例也由实测决定(早期设计给出"1 个 P 组配 4 个 CPU 节点"的比例,可作起点)

## 6. 单一入口(3 模型 + 多模态 + 可伸缩)

```
用户 ──(单端口 + API Key)──> [网关层:LiteLLM ×N(HA,VIP/Service)]──> 每模型一个稳定入口
                                                                     (K8s Service / 头less Service)
                                                                          │
                                                        ┌─────────────────┼─────────────────┐
                                                                  P 实例池(按模型分组)
```

* **网关**:LiteLLM Proxy ✓ —— 同名 `model_name` 写多条 ⇒ 组内均衡;`/v1/models` 只暴露 **3 个模型**
  (**虚拟密钥**按人/团队签发);多网关实例 + Redis 共享状态 ⇒ **无单点** ✓
  (文档:[Load Balancing](https://docs.litellm.ai/docs/proxy/load_balancing) · [Virtual Keys](https://docs.litellm.ai/docs/proxy/virtual_keys))
* **容器/编排**:K8s + **LMCache Operator**(上游提供)⇒ 副本数与自动伸缩交给编排层 ✓
* ⚠️ **动态成员**:LiteLLM 的 `model_list` 是**静态**的 ⇒ 建议**两级 LB**:
  网关只做"**模型路由 + 鉴权**",每个模型后面挂**一个 K8s Service**(其成员由编排层动态增删)✓
  ⇒ 这样**实例数变化不触碰网关配置** ✓(自动伸缩友好)
* ⚠️ **多模态声明**:客户端(如 DSH)需按模型声明 `input: [text, image]`,否则会被客户端侧拦掉(与本项目现状一致)

## 7. KV-cache pool(核心收益点)

**目标**:让"任何副本算过的前缀"在集群内**任何地方都能直接取用**,从而**免 prefill**。

**分层**(与 LMCache 的分层模型一致):

```
L0  GPU 显存(每实例私有,不可跨进程)
L1  节点 DRAM(每实例节点的 LMCache L1)
L1.5 集群 DRAM 池  ← 1600 台 CPU 节点的 DRAM(**≈2.4 PB**),经 RDMA 直读
L2  共享持久层(共享 FS / 对象存储 / Mooncake / NIXL)
```

**实现路径(与既有规划一致)**:

| 层 | 机制 | 备注 |
|---|---|---|
| L1.5 | **Mooncake Store**(`type: "mooncake_store"`,`protocol: "rdma"`) | Mooncake 本身即"**DRAM 池 + RDMA**"形态,与 1600 台 CPU 节点天然匹配;LMCache 侧为 L2 适配器 |
| 备选 | **NIXL Store** / **P2P**(`p2p_controller`) | 同一"位置"的其它候选;P2P 无中心 |
| L2 | `fs_native`(共享 FS)/ `S3` / `Valkey` | 成本最低的持久层 |

⚠️ **前置条件** ✓:Mooncake 需 `BUILD_MOONCAKE=1` 重编 LMCache,并部署其 **metadata / master** 服务;
RP(rdma)模式要求 LMCache 提供**有效的 L1 内存描述符**以预注册(上游另有 `--no-l1-use-lazy` 建议)。

**收益估算**(基于实测:重算 26.7 s / LMCache 命中 1.27 s,10K 前缀):

| 命中层 | 代价 | 相对重算 |
|---|---|---|
| L0(GPU 本地) | 0.35 s(实测) | ~76× |
| L1(节点 DRAM) | 1.27 s(实测) | ~21× |
| **L1.5(集群 DRAM 池,100 GB/s)** | **~20–100 ms(估算)** | **~300–1000×** |
| L2(共享 FS) | 视 FS 而定 | 仍远优于重算 |

⇒ **KV 池越快,负载均衡越自由**(无需前缀亲和,任意副本命中池) —— 这是整个设计的"设计杠杆"。

## 8. 自动伸缩(远景)

* **信号**:队列深度 / TTFT / L2 命中率 / GPU 利用率(本仓库已有指标栈,可直接作为 HPA 自定义指标)
* **对象**:按模型分组的 P 实例副本数;CPU 侧专家池/KV 池节点数
* **约束**:①**KV 池的容量与命中率**与实例数相互作用(实例越少,池命中越重要)
  ②缩容时**活跃序列不能被打断** ⇒ 只缩"无活跃序列"的实例
* **实现**:K8s HPA/自定义控制器 + LMCache Operator

## 9. 无单点(逐组件清单)

| 组件 | 单点风险 | 做法 |
|---|---|---|
| 网关 | 是 | **多副本 + VIP/Service**;状态放 Redis(多网关共享) |
| 模型入口 | 是 | 每模型一个 **K8s Service**,后端多实例 |
| LMCache 服务端 | 是 | 多台 + **`mp_coordinator`**(discovery/controllers) |
| **KV 池** | 是 | Mooncake 为分布式实现 ⇒ **配置副本/多实例**;或每机自带 L1 + 池兜底 |
| **专家池"一组"** | ⚠️ 早期设计已指出:"4 台里任意一台挂掉,整组不可用" | **每组≥2 组冗余** + 不可达时**降级**(退回本机/其它组) |
| 网络 | 是 | IB **双轨/多路径**;交换机冗余 |
| 权重/镜像 | — | 节点无状态化,可随时重建 |

## 10. 与硬件无关的硬约束(必须成立,否则不共享)

1. **KV 可互换**:同模型副本必须**完全一致** —— 权重与版本、vLLM 版本与补丁、KV dtype、TP、`max_model_len`、模型名
2. **缓存按模型分区**:不同模型 KV 形状/语义不同 ⇒ 不跨模型共享;但**池是共享的** ⇒ 容量按**三模型总工作集**规划
3. **池只做前后缀复用,不做逐步读取**(否则网络被打满,见 §4)
4. **decode 侧序列 KV 本地驻留**(同上)
5. **改动正交性**:我们的 V4.1"环形暂存组"补丁在 **connector 层**,池适配器在更下层 ⇒ **互不冲突**

## 5.5 同节点多实例能否共享 MoE 权重?(**同模型同参数前提下**)

**结论:今天不能;但改造成本小、收益大** ✓

### 现状(读引擎源码 `xiaotu_moe/csrc/moe/moe_v2.hpp` 得到)

| 事实 | 源码依据 | 含义 |
|---|---|---|
| 权重区是 **匿名 + MAP_PRIVATE** 映射 | `mmap(nullptr, total, PROT_READ\|PROT_WRITE, MAP_PRIVATE \| MAP_ANONYMOUS, -1, 0)` | ⇒ **每进程一份,跨进程不共享** ✗ |
| 进程内已是**单份**(不是每 socket 一份) | *"Single-copy NUMA sharding … Physical RSS is **ONE full copy** across all nodes and the virtual mapping is also 1x the weights"* | ✅ 单进程占用 = 1× 权重(非 2×) |
| 页的 NUMA 归属靠**首触** + `mbind` | *"writing faults the pages in on `node`, so every backed page is physically local"* | ⇒ 共享映射下**局部性仍可保持** ✓ |
| 权重区在填充后**只读** | 填充逻辑(`Fill per-socket replicas`)之后不再写 | ⇒ 可安全改为共享只读映射 ✓ |
| 全文件**没有**任何 shm/memfd/`MAP_SHARED` 权重后端 | 搜 `shm_open`/`memfd_create`/`MAP_SHARED` = 0 | ✗ 目前无共享通路(仅归约用 `/dev/shm`) |

⇒ **现状数字**:单实例 ≈ **137 GiB**;同节点 4 实例 ⇒ **≈548 GiB/节点** ✗

### 改造方案

**A(推荐,改动小)**:**把权重区改为"文件 / memfd 支撑的 `MAP_SHARED` 只读映射"**
* 缓存键 = 模型 + 配置 + 分片参数(如 `/dev/shm/xtu-moe-<hash>`);**首建者填充,其余直接映射** ✓
* 保留 `mbind` + 首触 ⇒ **物理内存共享且 NUMA 局部性不变** ✓
* 需要:首建者锁 / 引用计数 / 清理策略 ✓
