我来问一个问题，不影响你目前任何工作，这个项目，后续可以实现prefill设备独立，后端moe计算分散到4台双路服务器（nps=1，总node仍然是8）吗？假定prefill设备本身该能力很强不是瓶颈，但是decode不行，那么这几台服务器还需要GPU加速吗？性能预计折损如何？

好问题,而且它正好能用我们**已经测出来的数字**来回答,不需要猜。

## 一、架构上可行吗?——可行,而且和现有设计是同构的

引擎现在的做法就是 **"按 NUMA node 切分权重 + 跨 node all-reduce 归约"**(R2)。你描述的形态只是把"同一台机器里的 8 个 node"换成"4 台机器 × 2 node(NPS=1)",**逻辑拓扑一模一样**。

要改的只有一处:**归约后端**。

|               | 现在(单机 8 node)                  | 你说的形态(4 机 × 2 node)        |
| ------------- | ---------------------------------- | -------------------------------- |
| 归约通道      | `/dev/shm` + 自旋 barrier          | RDMA / RoCE 或 NCCL all-reduce   |
| 实测成本      | **~14 µs/层**                      | 预估 **15–40 µs/层**(含跨机跳数) |
| 每层数据量    | qlen×hidden×4B(qlen=4 → **64 KB**) | 同                               |
| 每 token 总量 | 43 层 × 64 KB ≈ **2.7 MB**         | 同                               |

⇒ **带宽完全不是问题**(100 tok/s 只需 ~270 MB/s 的网络);**真正的成本是延迟**:43 次跨机同步/token,合计 **+0.6 ~ 1.7 ms/token**。改动面也很局部——就是 `run_moe_and_ep` 里那段 EP 归约和 `EpShmState`,换成远程集合通信即可。

## 二、这几台服务器还需要 GPU 吗?——**MoE 侧不需要,注意力侧才是关键**

这是本项目最反直觉、但被实测反复确认的一点:

> **在当前这个工作负载里,GPU 的 16.8 ms 才是大头,CPU 的 MoE 反而不是。**

来自 0.1.0 的三段分解(C=1,12 层常驻):

复制

```
26.1 ms = 16.80(纯 GPU 地板:注意力 + dense + KV + 12 层常驻 MoE)
        +  7.4(31 层 CPU MoE,每层 0.24 ms)
        +  1.6(拷发)
```

所以:

- **MoE 后端 4 台 CPU 服务器完全不需要 GPU** —— 我们已经证明它的**边际带宽能打满 DRAM(692–768 GB/s)**,而 4 台机器聚合带宽是需求(100 tok/s 要 325 GB/s)的**近 10 倍**。
- **decode 侧要不要 GPU,取决于你愿不愿意把注意力搬到 CPU**:
  - **保留 GPU(强烈建议)**:GPU 只做 MLA/稀疏索引器/KV,MoE 全甩给 4 台 CPU 池 —— 这是最自然、收益最确定的形态。
  - **完全去 GPU**:KV 读量其实不大(8k 上下文下每 token 约 0.2 GB 量级,远小于 3.2 GB 的 MoE 权重),**带宽上放得下**;但 DS-V4 是 NSA 稀疏 MLA + Lightning Indexer,CPU 上**没有现成 kernel**(vLLM/lk 全是 CUDA),这块要自己写 —— 这是整个方案里风险最高的一环。

## 三、性能预计折损?——**在这个形态下大概率是提升,不是折损**

假设 decode 侧保留一张(甚至很小的)GPU 只跑注意力:

| 项             | 现在(1 机)         | 4 台 CPU 后端                                               |
| -------------- | ------------------ | ----------------------------------------------------------- |
| GPU 注意力地板 | 16.8 ms            | **16.8 ms**(不变)                                           |
| MoE            | 7.4 ms(31 层,单机) | **~2–4 ms**(4 台并行,理论上 1/4,实际受每层一次全局同步限制) |
| 拷发           | 1.6 ms             | ~0(无 D2H/H2D 往返)                                         |
| 跨机归约       | 0(shm)             | **+0.6 ~ 1.7 ms**                                           |
| **合计 TPOT**  | **26.1 ms**        | **≈ 20 – 22 ms**(45–50 tok/s 单流)                          |

原因很简单:**GPU 那 16.8 ms 占了 2/3,它才是瓶颈;把 MoE 铺到更大的 CPU 池只会让它更便宜。**

如果 decode 侧**完全去 GPU**(纯 CPU):

- MoE ~10 ms + 注意力(未知,**估计 15–40 ms**,取决于 CPU MLA 实现与上下文长度)+ 网络 1–2 ms
- 单流 TPOT 大概落在 **25–50 ms**(8k 上下文),短上下文可能 ~15 ms
- ⚠️ 但这是**估算**,因为 CPU 版 MLA 我们没有实测数据,不应作为结论

## 四、三个必须提前注意的坑

1. **NPS=1 与 NPS=4 不是一回事(铁律 R7)**。我们现在所有绑核/mbind 结论都是 NPS=4(每 socket 4 node,共 8 node)下得出的。改成 NPS=1 后**每个 socket 是一个 node**,跨 socket 访问在 BIOS 层面变成"跨 node" —— 引擎的 `mbind`/绑核策略要**按 socket 重新推导**,不能照搬。
2. **延迟结构完全不同**。同一台机器内的 8 个 node 共享一颗内存控制器域,`/dev/shm` 是物理内存拷贝;跨机是网络往返。**43 次/token 的同步延迟会成为新的固定成本上限**,这也是为什么"堆更多机器"对这个设计不一定线性收益。
3. **4–5 核/CCD 的规则依然成立(R1)**。decode 单流不需要 768 个核,它需要低延迟;**多出来的核不解决问题**,反而会抢 L3 与 power 预算。

**一句话结论**:你这个形态在带宽和算力上都绰绰有余,MoE 后端完全可以不用 GPU;**建议 decode 侧保留 GPU 只跑注意力**(那样性能预计从 26.1 ms 提升到 ~20–22 ms);真正的风险点是 **43 次/token 的跨机同步延迟** 和 **CPU 版 MLA 的实现**,而不是带宽。
