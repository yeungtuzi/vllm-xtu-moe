## 1. 内存带宽调查 + 编译器参数调查(已完成)

- 目标:①搞清楚 422 GB/s 是硬件问题还是测量问题;②回答"编译器还有没有 Zen4 优化空间"。
- 做法:新写 `report/stream_nt.c`(AVX-512 NT 存储 + first-touch + 可切线程数)与
  `report/rd1.c`(单流只读);对 STREAM 与 xiaotu CPU 引擎各做 5 组编译参数 A/B。
- 结果(详见 `EXPERIMENT_REPORT.md` §1.4a):
  * **内存规格 DDR5-4800 ×24 = 理论 921.6 GB/s;实测单流只读 860.5 GB/s(93%)、
    Triad+NT 743.6 GB/s(80%)** —— 与用户提到的 740 GB/s 一致。
  * 归因(2×2×2 矩阵):页放置 interleave→first-touch **+87%**、普通写→NT **+29%**、
    线程 192→96 **+15%**;向量宽度/`-ffast-math`/`-mtune` **无影响(<1%)**。
  * **编译器参数在两个目标上都没有可测收益**:STREAM 在 96 线程下已内存受限;
    CPU 引擎热循环是手写 AVX-512 BF16 内联函数。GCC 11.4 无 `-march=znver4`。
  * 顺带推翻一个旧结论:CPU 引擎每层只读到 3.2 GB/s、跑 0.64 TFLOP/s
    (AVX-512 BF16 峰值的 ~6%),**是反量化 ALU 受限,不是带宽受限**。
- 状态:**完成**。

## 3. 优化项 ⑤:MoE 内核计算率(已做 6 组实验,1 项落地)

- 目标:把单层 grouped MXFP4 GEMM 的算力利用率提上去。
- 做法与结果(T=16384,每层 ms;基线 198.1):

  | 变体 | ms/层 | 相对基线 |
  |---|---:|---:|
  | 基线(arith dequant + join/trans + BM=BN=BK=64 + 4 warps + NS=2) | 198.1 | 1.00× |
  | **down 内核 `sem="relaxed"` 原子加(已落地)** | **191.4** | **1.035×** |
  | even/odd-k 拆分成两次 `tl.dot`(去掉 join/trans) | 382.9 | 0.52× |
  | 反量化改 64 字节表 gather | 353.2 | 0.57× |
  | num_warps=2 / 8 | 252.7 / 229.5 | 0.79× / 0.87× |
  | NS=3 / BN=128 / BK=128 / BM=128 | 202.6 / 207.1 / 258.0 / 199.5 | ≤1.00× |

- **落地的一项**:`_down_kernel` 的输出累加用 `sem="relaxed"`(该 buffer 在本内核里
  是唯一访问,调用方在内核结束后才读,不需要 acq_rel)。T=16K:198.1 → 191.4 ms,
  吞吐 1923 → **1991 tok/s**;T=32K:2002 → **2066 tok/s**。golden 全通过。
- **量到的剩余机会**:把原子加换成"per-slot 缓冲 + 归约"可到 177.4 ms(再 +6.3%),
  但需要改 down 内核的输出布局,属下一轮。
- 结论:**这个 Triton 内核已在结构上的局部最优**,真正的数量级提升要靠换
  CUTLASS/CUDA 的 weight-stationary 内核(§7.2)。
- 状态:**完成(1 项落地 + 5 项证伪 + 1 项量化待做)**。

## 4. 优化项 ②:并发没有摊薄 H2D 地板(已定位,根因非插件)

- 目标:让同一 step 内的多个请求共享一次权重流,提升聚合吞吐。
- 做法:①给插件加 `XIAOTU_DEBUG_QLEN=1` 埋点,打印每个 MoE forward 的 qlen;
  ②写 `scripts/server_concurrency_test.py`,对真实 `vllm serve`(HTTP)发并发请求,
  并把 prompt 做成**首 token 就不同**(否则 vLLM 默认开启的 prefix cache 会直接命中,
  测出来的是缓存速度 —— 第一次测就踩了这个坑,c=8 假报 2003 tok/s)。
- **结果(HTTP,distinct prompts,2048 token × c)**:

  | c | 墙钟 | 聚合 tok/s | qlen 序列(每 step 的 token 数) |
  |---:|---:|---:|---|
  | 1 | 6.08 s | 337 | `[2111]` |
  | 2 | 11.25 s | 364 | `[2111]` + `[2111]` |
  | 4 | 13.83 s | 592 | `[2111]` + `[6333]` |
  | 8 | 24.87 s | 659 | `[2111]` + `[14777]` |

- **根因:请求到达时序,不是调度器策略。** 引擎一有第一个请求就立刻开 step;
  其余 N-1 个请求晚几毫秒到达,只能进下一个 step。所以**永远是"1 个独占一步 +
  其余合批一步"**,H2D 被流了 2 次(理论最小值的 2×)。
- 但**合批确实有效**:c=8 时 7 个请求共享一次权重流(14777 token / 16.4 s),
  比顺序执行(7×5.6 s)快 2.4×;聚合吞吐 337 → 659 tok/s(1.96×)。
- **上限**:单个 step 的成本是 `43 × max(127ms, 15.5ms+11.2µs×T) + attn(T)`,
  所以聚合吞吐的上界就是"一次大 prefill"的吞吐(16K 时 ≈ 900 tok/s,见 §5.9/§5.3)。
  并发不能让吞吐超过这个上界,只能把地板摊掉。
- **可改进的方向(需要上游)**:给调度器加一个微批窗口(几毫秒的 batching delay),
  让先到的请求等一等再开 step。估算收益 1.2–1.5×。**插件侧无法单独解决**。
- 状态:**完成(根因定位 + 量化;修复需上游调度器改动)**。

## 4b. 补充实验:预反量化到 BF16 能不能省掉反量化开销?

- 动机(用户提问):"内存足够大时,直接用 BF16 权重避免 fp4→bf16 反量化,是否能大幅提速?"
- 做法:`scripts/bench_cpu_engine_bf16.py` —— 同一层真实权重,同一路由,
  `MOE_MXFP4`(现场反量化)vs `MOE_BF16`(权重预先反量化成 bf16,12.9 GB/层)。
- 结果(B=2048,96 线程):

  | 权重格式 | 每层耗时 | 每 token | 实测算力 |
  |---|---:|---:|---:|
  | MXFP4(现场反量化,3.2 GB/层) | ~962–1160 ms | 0.47–0.57 ms | 0.53–0.64 TFLOP/s |
  | BF16(预先反量化,12.9 GB/层) | 956 ms | 0.47 ms | 0.65 TFLOP/s |

  ⇒ **只快 ~1.2×,不是数量级**。反量化最多占 ~17% 的时间。
- 更关键的发现:**引擎的每 token 成本随 batch 增大而恶化**(B=512 → 0.28 ms/token,
  B=2048 → 0.57 ms/token),说明瓶颈在引擎的 kernel 结构/scratch 行为
  (两种格式都只有峰值的 5–9%)。换权重格式解决不了,得换/重写 GEMM。
- 状态:**完成**。

## 5. 优化项 ①:内核级分解(结论:瓶颈不是注意力)

- 目标:把 16K 的非 MoE 部分从 9.65 s 压到 ≤6.4 s,端到端跨过 1500 tok/s。
- 做法:nsys 抓不到模型所在 worker 进程的 kernel(试了 3 次:`--capture-range=cudaProfilerApi`、
  NVTX range、`VLLM_ENABLE_V1_MULTIPROCESSING=0` 都只有零星事件),改成**插件内
  `torch.profiler` 钩子**(`XIAOTU_TORCH_PROFILE=<path>`,默认关闭),在 worker 进程里
  采样两次 16K prefill。
- **结果(2 次 pass 的 Self CUDA 合计 57.9 s)**:

  | 分组 | 每次 pass | 占比 |
  |---|---:|---:|
  | MoE 内核(本项目 gate_up + down) | 9.05 s | 31% |
  | 逐元素/其它(约 2700 个小内核/pass) | 8.35 s | 29% |
  | H2D memcpy | 5.47 s | 19% |
  | dense GEMM(o_proj fp8 einsum 1.57 / Marlin 0.92 / sgemm+bmm 0.73 / hc_prenorm 0.31) | 5.24 s | 18% |
  | **注意力 + indexer**(`_indexed_d512_split_*`/rope/sink) | **0.85 s** | **2.9%** |

- **重要更正**:第 1 轮用"TTFT − 单层微基准"推出的"注意力/indexer 占 9.7 s(69%)"
  是**减法伪影**;实测它们只占 2.9%。真正的剩余开销是"海量逐元素小内核 + dense GEMM
  + 未重叠的 H2D + 调度开销"。优化优先级随之改变:①减少/融合逐元素小内核
  ②o_proj fp8 einsum ③Marlin/sgemm ④H2D 重叠缺口 ⑤注意力(最后)。
- 状态:**完成(分解 + 优先级更正)**。数据:`report/prof16k_kernels.txt`。
