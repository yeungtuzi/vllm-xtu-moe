# 大模型服务集群 · 方案概览(面向非技术读者)

> **一句话**:把三个大模型的推理服务,做成一个**机房级的整体**;对外只给**一个地址、一把钥匙**,
> 对内让"**算过的东西尽量不重算**",从而**又快又省**,并且**任何一台机器坏掉都不影响服务**。

---

## 一、我们要解决什么问题

* 我们要对外提供 **3 个大模型**(都能看图)。它们**体型巨大**(每个上百 GB),**记忆力要求极高**(能读上百页的材料)。
* 用户提问时,常会**反复带上同样的一大段前情**(比如一份长文档、一段长代码)。如果每次都从头重读一遍,
  一次要**几十秒到几分钟** —— 慢,而且**白烧算力**。
* 单台机器**装不下、也扛不住**这样的规模。

---

## 二、系统长什么样(五个部分)

```
       用户
        │  一个地址 + 一把钥匙
        ▼
 ┌──────────────────┐
 │  ① 接待处(网关) │  验证钥匙 · 按"要哪个模型"分派
 └────────┬─────────┘
          │
 ┌────────▼─────────┐         ┌────────────────────┐
 │ ② 算力区          │◄───────►│ ④ 共享笔记本        │
 │ 160 台 GPU 服务器 │  高速   │ (缓存池)            │
 │ 负责"读懂"与"专注"│  通道   │ 谁算过,大家都能用   │
 └────────┬─────────┘         └─────────▲──────────┘
          │                              │
 ┌────────▼─────────┐                    │
 │ ③ 专家区          │────────────────────┘
 │ 1600 台 CPU 服务器│ 负责"查书"式的重活;每台都备一整套书
 └──────────────────┘
        ▲
        │ ⑤ 100 GB/s 高速网络(把所有机器连成一体)
```

| # | 部分 | 通俗说法 | 干什么 |
|---|---|---|---|
| ① | **接待处** | 酒店前台 | 只开**一个门**;**一把钥匙**通行;按你要的模型分派到后面 |
| ② | **算力区** | 最会思考的团队 | **读懂材料**(预填充)与**持续专注**(注意力);需要专用加速卡 |
| ③ | **专家区** | 遍布全城的图书馆 | 模型里"查书"式的大量重复计算;**每台都备一整套书**,所以谁都能立刻作答 |
| ④ | **共享笔记本** | 全公司共用的草稿本 | **任何一台算过的内容,别台可以直接取用**,不必重算 |
| ⑤ | **高速网络** | 极宽的内部走廊 | 让"取草稿本"只要**毫秒级**;这正是一整本厚草稿能秒级送达的前提 |

---

## 三、这样做的好处

1. **快**:重复的长前情**不再重读**。我们实测过:同样一段前缀,重新计算要 **26.7 秒**,
   从共享笔记本取用只要 **1.27 秒**;把笔记本做到集群级 + 高速网络后,预期可降到**几十毫秒**。
2. **省**:"算过的结果只存一份、大家共用";另外同一台机器上的多个服务实例**共用同一套模型权重**
   (方案已定,见技术文档),不重复占内存。
3. **对外极简**:用户只需**一个地址 + 一把钥匙**,就能用三个模型;**换/加机器对用户完全透明**。
4. **弹性**:业务忙时多开、闲时少开(**按需自动启停**),把算力与电费花在真正需要的时候。
5. **不中断**:每个环节都做了冗余(**没有单点**);某台机器故障时,请求会被自动转到其它机器。
6. **能看图**:三个模型都支持图片输入(视频当前不支持;可用"抽帧成多张图"的等效方式)。

## 四、风险与前提(如实列出)

| 风险 | 说明 | 我们的应对 |
|---|---|---|
| **还只是设计,没实测** | 目前**未做任何实验**;几个关键数字(跨机通信延迟、CPU 侧吞吐、缓存池实测带宽)是**推算** | 按**分阶段**推进:先单机多实例 → 两机 → 小规模缓存池 → 再接网关;每步都有**明确判据** |
| **网络是命脉** | 共享笔记本的收益完全依赖那条高速通道;拥塞或故障会让收益下降 | 通道**冗余/双路**;并做流量预算,避免"大文件传输"挤掉"小消息" |
| **缓存不是万能的** | ①内容**超出笔记本容量**时仍需重算 ②**正在进行中的对话**必须留在本机内存里 ⇒ 单会话能记多长,由本机内存决定 | 按"**总工作集**"规划容量;分层设计(最热在内存、其余在磁盘) |
| **配置必须严格一致** | 同一模型的多个副本若配置不一致,可能取到"**别的版本算的结果**",导致答错 | 强制同配置;发布与升级走统一流程;并在网关侧做分组约束 |
| **技术复杂度高** | 组件多(网关、缓存池、编排、专用网络库),需要**专业运维**(容器编排 + 高速网络) | 分阶段引入;**先小后大**;每一层都保留"降级但可用"的退路 |
| **成本** | 160 台加速卡服务器 + 1600 台 CPU 服务器,采购/电力/机房都是大投入 | 用**自动伸缩**降低闲置;并先在小规模验证"命中率→收益"再扩容 |
| **依赖外部组件** | 关键能力来自开源项目(如 LMCache、Mooncake 等),我们还需自行打补丁并**定期跟上上游** | 已有的补丁与流程已文档化;升级按固定流程做**回归验证** |
| **单点需演练** | 设计上已逐项冗余,但"真坏一台会怎样"必须**实际演练**才算数 | 列入验收清单:故障演练 + 无单点验证 |

---

## 五、结论与下一步

* **结论**:方案**可行且收益明确** —— 对外一个入口、对内一套共享记忆,既提速又降本,并具备弹性与冗余。
* **但它现在仍是"设计"**,所有收益数字中只有一部分是我们**实测**过的(单机场景),集群规模部分是**推算**。
* **下一步(建议顺序)**:① 单机多实例共享一份缓存(验证跨实例命中)
  ② 标定关键参数 ③ 两机原型(量出跨机通信真实延迟)④ 引入小规模缓存池 ⑤ 接上网关与编排
  ⑥ 最后做大规模扩容与故障演练。
* 详细的技术依据、实测数据与待验证清单,见技术文档《大规模集群设计》。
