### 待优化清单(按性价比)
1. **解码每线程交付带宽**:**1.32 vs 2.21 GB/s·线程**(DEDUP=12 微基准;整机带宽我们 2.25× 而实测效率只有参考的 ~40%)
   —— 解码差距的主因。注意:两边**都不是带宽受限**(实测仅达带宽下界的 12% vs 28%),所以"带宽 2.25×"不会自动兑现;
   若效率追平参考,`4.25 GB/token ÷ (0.28×740 GB/s) ≈ 20.5 ms ⇒ ~49 t/s`(§511)。
2. **Patch B(逐层 load/slice/release)** —— 见 §3,一并解 NPS4 OOM + 峰值内存。
3. **长序列工作区预算** —— 修 32K OOM(违反优先级 1 的真问题)。
4. **冷启动预热** —— 逐形状 Triton JIT 未预热(生产首个未见长度会卡 20–60 s)。
5. **CED 预填充捷径**(**仅 V4.1**)—— 报告:预填充只需前一半(编码器 20 层)+ 最后 128 token 的 SWA 重放;
   本机 vLLM **未实现**(全树无 `causal_encoder`/`bounded_replay`)⇒ 现在付约 2× 预填充算力,是最大的未动用优化。
6. **R113 线程池丢票构造性修复** —— 第一半(flat 无损账)已落地;协议重设计未做,当前只能用保守线程配置。
7. 常驻层数(受优先级 1 约束,1M 下真实上限 2–6 之间,需试)、spec 参数扫描、`num_prompts`/并发曲线。

## 3. 已知坑与限制(别踩第二次)
* **NPS=4 的 OOM 不是"没调好"**:根因是 vLLM **一次性物化全部专家权重**并以未绑定 first-touch 分配堆在单个 node 上
  (`oom-kill: nodemask=0, anon-rss:236289496kB`)。今天的缓解是 `numactl --interleave=all`;
  **结构性解法 = Patch B**(我们的 `RELEASE_SOURCE` 只在"全部物化完之后"逐层释放 ⇒ **峰值仍包含所有源张量**:
  实测峰值 702 GiB vs 必要 ~467 GiB)。
* **NPS 现在与我们的分片数无关**(按 socket 分片)⇒ 光改 BIOS 不回退也不改善;要用 node 分片须
  `XIAOTU_MOE_SHARD_BY_NODE=1` + NPS4(§512)。
* **测量口径**:ShareGPT 基准有 ~10–15% run-to-run 波动 ⇒ 用 `report/tuning/sharegpt16.json` 这个固定集;
  长上下文 TTFT **必须多次热身**后才可取稳态;`bench_lat.sh` 用随机 token,**不能**用来评价投机解码收益。
* **不许从 env 开关反推能力**(R-VERIFY):GPU 预填充曾被误判为"要额外占 253 GiB/rank 主机内存",
  真相是活跃路径从引擎分片流式、**零额外主机内存**、显存只占 ping/pong 两槽。
