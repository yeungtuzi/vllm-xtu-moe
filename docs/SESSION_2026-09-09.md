## 二、数值正确性根因与修复(本会话最大成果)

**症状**:真实权重下 `attn_out = inf` → 全部 token_id = 0;8192 token 的 profile pass 反而
"正常",因为 `attn_metadata is None` 时 `forward_mqa` 走 `output.zero_()`(设计行为)。

**定位链(逐层埋点 `XIAOTU_DEBUG_L3/L4`)**:
`embed` 非零 → mHC pre 正常(pm/rm 非零)→ `o_padded` 有限(0.29,无 inf/nan,稀疏 MLA 本身没问题)
→ **`o_proj_out = inf`**。

**根因**:SM80 无 fp8 tensor core → 主线 fp8 block 量化 dense linear 落到
`MarlinFP8ScaledMMLinearKernel`,`prepare_fp8_layer_for_marlin` 把 `wo_a.weight`
**重打包成 Marlin 私有 int32 布局**;而 DS-V4 的 o_proj 绕过 `linear.apply`,直接读
`wo_a.weight` 做 fp8 einsum → 读到打包后的乱数据 → 反量化出巨值 → inf。

**修复(采用 fork 官方修法,commit `971c27995`)**:
1. `vllm/model_executor/layers/quantization/fp8.py`:`process_weights_after_loading` 里特判
   `getattr(layer, "is_bmm", False)` → 不做 Marlin 重打包,把 block-fp8 权重就地反量化成
   **bf16 [N,K]** 并 `use_marlin = False`;
2. `vllm/models/deepseek_v4/nvidia/ops/o_proj.py` 换成 fork 原版(走
   `deepseek_v4_fp8_einsum`,内含 SM80 的 `DECODE_E4M3` + `B_BF16` 两条路径),
   删掉此前手写的 torch 反量化 fallback(它对 Marlin 打包布局是错的);
3. 顺带按 fork 补齐:`has_cutedsl()` 在 SM8.x 返回 False;`sparse_mla.py`
   `supports_compute_capability` 接受 major==8。

**验证**:
- `"The capital of France is"` → `" Paris. The capital of Spain is Madrid"`(token_ids
  `[11111,16,455,6102,294,16603,344,29168]`);64 token 生成完全连贯;
- 测试服 `/v1/completions` 同样正确(见第五节)。

## 三、性能数据(真实权重,GPU2,`VLLM_EXPERTS_LOAD_DEVICE=cpu`,OMP=96,prod 同时在跑)

直连 `LLM.generate`(maxlen 256,32 输出 token):

| B | tok/s(输出) |
|---:|---:|
| 1 | 6.9 |
| 32 | 70.8 |
| 64 | 74.6 |
| 128 | 80.3 |
| 256 | 77.6 |

**瓶颈分析**(埋点 `XIAOTU_TIMING=1`,每 43 层打印):
- 每步 `layer_43x ≈ 1.13s`(B=128),其中 `attn_43layers ≈ 0.10s`(8%);
- `engine.cpu_decode` 调用本身 3ms(异步:内部 D2H → host function 跑 CPU MoE → H2D);
- 即 **CPU MoE ≈ 90% 的每步时间**,GPU 注意力只占 8%;
- 引擎权重读取是 DRAM 带宽瓶颈(fp4 权重 ~155GB/step,EPYC 9654 12ch DDR5),
  B≥128 后专家不再复用 → 吞吐在 ~80 tok/s 饱和。

**cudagraph 不适用(实测)**:`FULL_DECODE_ONLY` 让 B=128 从 80 tok/s 掉到 **20.17 tok/s**。
原因:引擎 binding 把 `qlen/outg` 等可变状态存在 per-engine 结构里,host function 在**回放时**
读取;多 bucket 捕获后 `st->qlen` 变成最后一个 bucket(512)→ 每步做 4x 无用计算。
(输出仍正确,因为前 128 个 token 的数据是对的。)→ 继续 `--enforce-eager`。

**顺带修掉的越界隐患**:`forward_many_m` 用 `token_id(<qlen)` 直接索引按 `group_max_len`
分配的 `input_fp32_/gate_input_/…`,所以必须 `group_max_len >= qlen`。此前 profile pass
`qlen=8192` 而 `group_max_len=4224` → **堆越界约 2x**。现在插件按
`min(4096, max_num_batched_tokens)+128` 自动算,并在超界时打 WARNING;测试脚本统一
`--max-num-batched-tokens 4096`(构造时间 265s → 200.7s)。

## 四、参考基线(fork README)

| 机型 | GPU | 内存 | Prefill | Decode | +投机 |
|---|---|---|---:|---:|---:|
| Lvllmds4-x v2.3.9(SM80 分支) | 3090×2 | DDR4-3200 16ch | 1060 t/s | **26 t/s**(input 32768) | 35~47 t/s |
| Lvllmds4 v2.3.9(SM120) | PRO 6000×1 | DDR5-4800 24ch | 3100 t/s | 75 t/s | **100~115 t/s** |

→ 用户提到的 "~100 tok/s" 来自 **SM120 + 投机解码**那一行;SM80 分支公开数据是 26 t/s
(input 32768)。我们在 A100 + 短上下文、无投机下已到 80 tok/s(测试服 82),但**上下文长度
与机型不可直接比**。

## 五、测试服(8071)

- 启动:`scripts/serve_8071.sh`(GPU2、端口 8071、`HF_HUB_OFFLINE=1`、OMP=96、
  maxlen 1024、max-num-seqs 64、max-num-batched-tokens 4096、`--enforce-eager`、
  `--kernel-config.enable_jit_warmup=false`)。
- 注意:默认 JIT warmup 在 SM80 会编译一个用 `tl.float8e4nv` 的内核而直接失败
  (`kernel_warmup.py` → `jit_warmup_registry.warmup`),故测试服关闭 jit warmup
  (首个请求付 JIT 成本,功能/数值不受影响)。
- 校验:`scripts/check_8071.sh`(单请求)、`scripts/load_8071.py`(并发压测)。

结果:

   Portugal is Lisbon. The capital of Germany is Berlin. The capital"

## 七、引擎内存模式与阶段分析(补充)

- 引擎(重写版 `MOE_V2`)权重驻留模式实测(43 层 × 每层一个引擎实例):
  | 模式 | EngineCore RSS | N=64 吞吐 |
  |---|---:|---:|
  | 默认(NUMA 分片/回退复制) | 844 GB | 82.35 tok/s |
  | `XIAOTU_MOE_SINGLECOPY=1` | **331 GB** | 68.88 tok/s |
  `scripts/serve_8071.sh` 已把它做成 env 开关(默认 1,内存优先;追求吞吐置 0)。
- 引擎自带分析器 `XIAOTU_MOE_PROFILE=1`(每 40 次调用打印一次):
  单请求态(na≈8 活跃专家、M≈118 实例)A≈32.5ms/层、B≈13.5ms/层 → 46ms/层;
  此时每层只读 ~100MB 权重 → 有效带宽 ~2GB/s,说明**小 batch 是延迟/并行度受限**;
  大 batch(B=128、全 256 专家、3.2GB/层)才接近 DRAM 带宽上限。
