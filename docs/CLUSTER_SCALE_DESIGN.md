# 集群扩展初步设计:MoE 专家池横向扩展(scale-out)+ 注意力/预填充留在 GPU

> **状态**:初步设计(v0.1 草案)。所有**实测**数字都来自本仓库 `report/tuning/NOTES.md` 与
> `docs/REPORT_vllm-xtu-moe.md`;凡标注**估算**的都没有实测支撑。
> **日期**:2026-09-14

---

## 0. 先澄清术语:这是 **scale out**,不是 scale up

| | scale up(纵向) | **scale out(横向)** |
|---|---|---|
| 做法 | 单机加资源:更多核 / 更多内存通道 / 更大显存 | **加机器**:多台主机 + 网络互联 |
| 边界 | 一个 OS、一个故障域、一颗内存控制器域 | 多个 OS、多个故障域、**网络成为新的延迟来源** |
| 本机例子 | 把 NPS=4 改成 NPS=1、把 12 通道换成 24 通道 | 从 1 台双路机器 → 4 台双路机器 |

我们讨论的形态更精确的名字是 **"异构函数级解耦"(functional disaggregation)的 scale-out**:

```
                ┌──────────── 前段(1 台,带 GPU) ────────────┐
                │  分词 / 路由 / 注意力(MLA+稀疏索引器)/ KV  │
                │  (可选)若干"常驻 GPU"的 MoE 层             │
                └───────────────────┬────────────────────────┘
                                    │ 每层:6 个专家的激活 + 部分和归约
        ┌───────────┬───────────────┼───────────────┬───────────┐
        ▼           ▼               ▼               ▼
   专家节点 0    专家节点 1      专家节点 2      专家节点 3
   (双路,NPS=1) (双路,NPS=1)   (双路,NPS=1)   (双路,NPS=1)
   2 NUMA node   2 NUMA node     2 NUMA node     2 NUMA node
   └──── 合计 8 个 NUMA node = 一个 EP 组 ────┘
```

* 这**不是**对称集群:前段负责"稠密/延迟敏感"的部分,4 个节点负责"稀疏/带宽敏感"的专家计算。
* 与业界 **P/D 分离(prefill/decode disaggregation)** 的关系:那是把 prefill 与 decode 分到不同实例;
  **我们多走一步:把 MoE 计算也从 decode 实例里分出去**。

## 1. 目标与硬约束

**目标**:在**不换 GPU 代际**的前提下,用 4 台商用双路服务器把可服务的上下文长度与并发吞吐放大,
同时**不牺牲单流延迟**。

**继承的硬约束(铁律,见 `report/tuning/IRON_RULES.md`)**:

| # | 约束 | 为什么 |
|---|---|---|
| R1 | **每 CCD 只用 4–5 核** | 更多核不增带宽,只抢 L3/power(实测 −40%) |
| R2 | **按 NUMA node 切分权重,每个 node 只读写本地内存**,跨 node 只交换小部分和 | 单机实测:不切核 9.8 ms/层,跨 socket 33 ms/层 |
| R7 | NPS=1 / NPS=4 **不是一回事**;locality 的真实边界是 **socket**,跨机则是**网络** | 现有全部绑核/mbind 结论都在 NPS=4 下得出 |
| R8 | 先算 roofline:43 层 × 75.5 MB = **3.246 GB/token** | 21.5/50/100 tok/s 需要 70/162/325 GB/s |

**新增约束(本设计提出)**:

* **N1**:每个 token 的 43 层**必须串行** ⇒ 跨机同步次数 = **43 次/token**,
  **同步延迟(不是带宽)是新的天花板**。
* **N2**:层与层之间**不能**按机器流水(那只增吞吐、不降单流延迟);能并行的是**同一层内的专家**。
* **N3**:前段的 GPU 一旦承担注意力/KV,**专家节点就不需要 GPU**。

## 3. 通信设计(唯一必须新写的部分)

现在 EP 归约走 `/dev/shm` + 自旋 barrier(**同机**)。跨机必须换成网络。**变化面很小**,
只有 `run_moe_and_ep` 的归约与 `EpShmState` 这一层。

| 方案 | 每层延迟(估) | 备注 |
|---|---|---|
| **A. NCCL/RCCL all-reduce**(8 rank,跨 4 机) | 20–60 µs | 复用上游,成熟;但 `all_reduce` 对小消息(64 KB)是**延迟**主导 |
| **B. 点对点 reduce-to-front + broadcast** | 15–40 µs | 前段是天然聚合点;省掉 all-reduce 的两次往返 |
| **C. RDMA write + 前段自旋**(自定义) | 10–25 µs | 最快,但要自己写(违反"复用优先") |

**推荐 A 起步、B 为优化目标**。数据量极小,不需要考虑带宽:

```
每层每 token 的归约量 = hidden × 4B = 16 KB(qlen=1)/ 64 KB(qlen=4)
43 层合计 ≈ 0.7–2.7 MB/token
100 tok/s ⇒ 70–270 MB/s(100 GbE 都用不到 3%)
```

⇒ **网络只需要低延迟,不需要高带宽**;25–100 GbE + RoCE 足够,不需要 InfiniBand。

**L 型补充**:激活只有 `hidden × 2B = 8 KB/token`,前段↔专家节点传激活的开销可忽略;
要传的是 **top-k 的 expert id + 权重**(≤ 64 B/token)。

## 4. 带宽与容量预算

### 4.1 4 台双路服务器(每台 ≈ 本机的一半)

| | 单台 | 4 台合计 | 需求(100 tok/s) | 余量 |
|---|---|---|---|---|
| 内存带宽 | ~700 GB/s | **~2.8 TB/s** | 325 GB/s | **8.6×** |
| DRAM 容量 | 1.5 TB | 6 TB | 权重 137 GiB(全模型) | 充裕 |
| 核数 | 192 | 768 | 见 R1(实际只用 4–5 核/CCD) | **严重过剩** |

⚠️ **核数过剩是陷阱**:R1 已经证明多开核**反而更慢**。专家池的收益来自**带宽**与**分摊固定成本**,
不是来自核数。

### 4.2 关于"在其中一台上插一张 RTX PRO 6000 / 5090 96GB"

**可以,而且这是本设计里最推荐的一种落地形态**(见 §5)。

| 资源 | 96 GB 卡的分配(估) | 依据 |
|---|---|---|
| 非专家权重(注意力+dense) | **6 GB** | 实测 5.96 GiB |
| KV(8k 上下文) | 30–40 GB ⇒ **~150–200k token** | 0.196 MiB/token 实测外推 |
| 工作区/激活/图 | 5–8 GB | — |
| **剩余可放常驻专家层** | **~45 GB ⇒ 14 层**(TP=1,每层 3.2 GiB) | 每层 −0.70 ms/token |

⇒ 相比现在 2×A100-40GB 的 **12 层常驻**,96 GB 单卡可以做到 **~14 层**,并且 **KV 从 22 GiB 提到 30–40 GB**。

**但有两个必须正视的坑**:

1. **架构不匹配**:RTX PRO 6000 / 5090 是 **SM120(Blackwell)/ SM89**。
   本项目**全部 kernel 与补丁都在 SM80(A100)上验证**;DS-V4 的稀疏 MLA 在 SM120 上走的是
   **另一条 vLLM 代码路径**(参考 lk 生态里 `jasl/vllm` 的 `codex/ds4-sm120-min-enable` 分支)。
   ⇒ **我们的 SM80 补丁不能直接套用**,需要单独的适配工作(见 §7 风险)。
2. **单卡 = TP=1**:不再有跨卡 all-reduce(好事),但每层专家权重从 1.6 GiB 变成 **3.2 GiB**,
   常驻层数按此折算;另外消费卡的 **P2P/NVLink 缺失**在这里不影响(MoE 在 CPU,GPU 只做注意力)。

## 5. 两种拓扑方案的对比

### 方案 A:4 台 CPU 专家节点 + 1 台独立 GPU 前段(5 台)

```
[GPU 前段: 2×A100-40GB 或 1×96GB]  ← 注意力 / KV / 预填充 / (可选)常驻层
        │
   ┌────┴────┬─────────┬─────────┐
 [专家0]   [专家1]   [专家2]   [专家3]
```
* 优点:GPU 节点可以按需升级(现有 A100 可继续用);专家池可独立扩容。
* 缺点:多一台机器;GPU 节点的 CPU 基本闲置。

### 方案 B(推荐):4 台双路服务器,**其中 1 台插 96 GB 卡**

```
[节点 0: 双路 + 1×96GB GPU]  ← 同时是前段(注意力/KV/预填充)与专家节点之一
        │
   ┌────┴────┬─────────┐
 [专家1]   [专家2]   [专家3]
```
* **优点**:
  1. **4 台就是一组**(8 个 NUMA node,与现有 `nshard_=8` 的切分方式**天然同构**);
  2. GPU 节点的 **CPU 仍可作为专家池的一部分**贡献带宽(它的 24 通道不浪费);
  3. 机柜/交换机/运维成本最低。
* **缺点**:GPU 节点是**混合角色**,它的 CPU 要同时服务本机注意力的调度 +
  自己那份专家计算 ⇒ 需要在**核隔离**上做文章(例如把 4–5 核/CCD 中的一部分固定给专家引擎,
  其余给 vLLM 的调度线程)。这正是 R1 的直接应用。
* ⚠️ 注意:GPU 节点的 PCIe 带宽被 KV/激活占据,而它的 CPU 又要读**本机 DRAM** ——
  两者争的是**不同的资源**(PCIe vs 内存通道),所以可以共存。

**结论**:
* **MoE 侧完全不需要 GPU**(已由 v0.1 实测证明:专家权重的边际带宽能打满 DRAM);
* **注意力/KV 强烈建议留在 GPU**(它的 16.8 ms/token 是当前成本的 2/3,但它是**延迟敏感 + 需要 kernel 支持**的部分);
* ⇒ 方案 B 是"4 台为一组"的最自然形态。

## 6. 性能预估(明确区分实测与估算)

### 6.1 单流 C=1

```
现在(1 台 + 2×A100,12 层常驻):
    26.1 ms = 16.8(GPU 注意力等) + 7.4(31 层 CPU MoE) + 1.6(拷发)

方案 B(4 台一组,1 台带 96GB 卡,~14 层常驻):
    GPU 段        ≈ 16.8  ←   不变(注意力还是那张卡在做)
    常驻层 +2     ≈ −1.4  ←   实测每层 −0.70 ms
    MoE 段        29 层分摊到 4 台 ⇒ 每层字节降到 1/4,
                  但 **A=0.124 ms/层的固定成本不可分摊**(N1/N2)
                  ≈ 29 × (0.124 + 0.013) ≈ 4.0 ms   (现在是 7.4)
    跨机同步      ≈ 43 × 25 µs ≈ 1.1 ms               (估算,A 方案)
    拷发          ≈ 0(专家不在本机,D2H/H2D 消失;换成 8 KB/token 的网络激活传输)
    ────────────────────────────────────────────
    合计          ≈ 20.5 ms  ⇒  ~49 tok/s 单流
```

⇒ **单流是"持平略好"**(26.1 → ~20.5 ms),**不是数量级提升**。原因很清楚:
**GPU 那 16.8 ms 占 2/3,而每层的固定成本 A 不随节点数下降。**

### 6.2 并发吞吐

| 并发 | 现在(fork 路径实测) | 方案 B(估算) | 理由 |
|---|---|---|---|
| C=1 | 35.0 t/s | ~49 t/s | 见上 |
| C=2 | 64.3 t/s | ~95 t/s | 字节项分摊更好 |
| C=4 | **107.3 t/s** | **~180–220 t/s** | 4 台带宽 2.8 TB/s,MoE 不再是瓶颈 |

⚠️ **C≥4 的估算是没有实测支撑的**,给出区间是因为跨机同步在批量下会与计算重叠(收益)也可能
因为集合通信的 rank 数变多而变差(风险)。

### 6.3 什么**不会**改善(必须写清楚,避免误区)

* **单流延迟不会因为"堆 4 台"而线性下降** —— 43 层串行 + 每层固定成本是硬边界;
* **上下文长度的上限由前段显存决定**,不由专家池决定(专家池只影响吞吐);
* **核数不是瓶颈**(R1),把 768 核全用上只会更慢。

## 8. 风险与未验证项(诚实清单)

| 风险 | 说明 | 缓解 |
|---|---|---|
| **跨机同步延迟未知** | 全部收益都压在"每层 20–40 µs"这个估算上;本机 `/dev/shm` 是 14 µs,**跨机没有实测** | P1 第一天就量它;若 >100 µs/层,整个方案的单流收益会被吃掉 |
| **NPS=1 的绑核策略要重推** | 现有 R1/R2 的结论都在 NPS=4 下得到;`mbind`/CCD 排序可能都要改 | 先在同机上用 NPS=1 复测一遍引擎标定 |
| **SM120/SM89 适配** | 96 GB 消费卡与我们的 SM80 补丁不同源;稀疏 MLA 走另一条路径 | P3 之前先确认 vLLM 主线在该卡上能否跑通 DS-V4 |
| **混合角色的核争抢**(方案 B) | GPU 节点既要调度注意力、又要跑自己那份专家 | 用 `taskset`/`numactl` 把专家引擎的核与 vLLM 线程**物理隔离** |
| **故障域变大** | 4 台里任意一台挂掉,整组不可用 | 前段做超时降级:专家节点不可达时退回"本机全量 CPU MoE"(慢但不挂) |
| **每层固定成本 A 不可分摊** | A ≈ 0.124 ms × 43 ≈ 5.3 ms **无论多少台机器都不变** | 想再降只能改引擎内核(见 v0.2 的 P0 目标) |

## 9. 一句话结论

> **可行,而且是 scale-out**;形态上最自然的是 **"4 台双路服务器为一组,其中一台插 96 GB 卡"**:
> GPU 负责注意力/KV/预填充(并顺便多放 2 层常驻),4 台的 CPU 共同承担 43 层 MoE。
> **MoE 侧不需要 GPU**;预期**单流 20–22 ms(约 49 tok/s)、C=4 聚合 180–220 tok/s**。
> 真正的风险只有两个:**43 次/token 的跨机同步延迟**(未实测)与**消费卡的 SM120 适配**。
> 而**每层固定成本 A ≈ 0.124 ms 不随节点数下降** —— 这条瓶颈只能靠改内核解决,不能靠加机器。
